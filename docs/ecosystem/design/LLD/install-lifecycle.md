# LLD — Install lifecycle

**Purpose**: install/uninstall/enable/disable/update/rollback/deprecate/delete-draft, plus sharing, reporting, and admin-side force-disable and featured overrides. Landed in tasks B-10, B-19 (M2).

## Files / functions
- `services/ecosystem/installs_service.py` (task B-10) — `install()`, `uninstall()`, `set_enabled()`, `update_to_version()`, `rollback()` (an alias for `update_to_version` — rollback is "update to an older, still-immutable version," not a distinct mechanism), `get_install()`, `get_install_for_caller()`, `list_installs()`, `cleanup_installs_for_inactive_users()` (item 4d, pre-M3).
- `services/ecosystem/policy_service.py` (task B-19) — `share()`/`unshare()`, `report()` (with the N-report auto-hide threshold), `force_disable()`/`unyank()` (map to `ecosystem_items.status='yanked'`/`'active'`), `set_featured_override()`/`delete_featured_override()`, `require_item()`/`unrequire_item()` (Review round following M1, item F — promotes/demotes existing `provisioned` installs to/from `required`), and `admin_disable_org_default()`/`admin_restore_org_default()`/`is_org_default_excluded()` (item 4a, pre-M3 — see "Lazy provisioning" below).
- `services/ecosystem/items_service.py`'s `compute_allowed_actions()` — the single source of truth for CONTRACTS.md §6's per-caller action array, a pure function taking the item/install/caller context as plain arguments (no DB access) so it's trivially unit-testable and so every call site (router, future admin screens) derives the same answer the same way.
- `routers/ecosystem_router.py` — thin HTTP glue for all of the above; `_handle_ecosystem_error()` maps each typed service exception to its documented wire error code.

## API and DB changes
Uses `ecosystem_installs`/`ecosystem_shares`/`ecosystem_reports`/`ecosystem_featured_overrides` from task B-1 as-is. `ecosystem_items.status`'s `'yanked'` value is used for both its original meaning (upstream-source-initiated removal) and admin-initiated `force_disable` — a single value covers both cases; there's no field distinguishing which caused it, since `allowed_actions`'s `unyank` action correctly applies to either origin, and no other current behavior needs to tell them apart.

**New in item 4 (pre-M3)**: `ecosystem_org_excluded_defaults(org_id, item_id, excluded_by, excluded_at)` — one new, additive table (`db/migrate.py`'s `_part_ad3_ecosystem_org_excluded_defaults_2026_09_27()`), PK `(org_id, item_id)`, `item_id` FK to `ecosystem_items`. See "Lazy provisioning" below for what it's for.

## Lazy provisioning (item 4, pre-M3)

The actual lazy-provisioning *mechanism* — a per-caller `INSERT ... ON CONFLICT DO NOTHING` sweep on every `GET /ecosystem/config` call — is task B-12's (M3), not built yet (`services/ecosystem/config_service.py` is still a stub). This section documents the four behaviors that mechanism must satisfy, and what's already real vs. still deferred, per `CONFIG_AND_PRODUCTS.md` §12.

**(a) Admin org-level disable/remove of a default applies to all users immediately.** `policy_service.admin_disable_org_default(item_id, org_id, disabled_by)` does two things, both real today, independent of B-12:
1. `UPDATE ecosystem_installs SET enabled=false WHERE item_id=... AND org_id=... AND origin IN ('provisioned','required') AND enabled=true` — every already-provisioned user in that org is disabled in one statement, not a per-user loop the caller has to drive. Deliberately includes `origin='required'` rows too: an admin explicitly removing a default overrides the required-lock (which only exists to stop a *user's own* disable action, not an admin's).
2. Inserts a row into `ecosystem_org_excluded_defaults` (idempotent — a duplicate-key insert is caught and ignored, not an error). This is the part that only matters *once B-12 exists*: `policy_service.is_org_default_excluded(item_id, org_id)` is the check that mechanism's sweep must call before creating a new `provisioned` row for a not-yet-provisioned user — without it, a brand-new org member would silently get the excluded default re-provisioned on their very first request, since nothing about their absence of an install row distinguishes "never provisioned" from "was provisioned, then the org excluded this default." `admin_restore_org_default(item_id, org_id)` reverses the exclusion for future provisioning — **disclosed, deliberate limitation**: it does not retroactively re-enable already-disabled installs (an `enabled=false` flag alone can't tell "admin disabled this as part of the org-wide removal" apart from "this specific user disabled it themselves, independently, earlier" — a future admin-tooling task that wants "restore means re-enable for everyone" needs its own marker to distinguish the two; not built here since nothing currently reads that distinction).

**(b) Required items cannot be disabled or uninstalled by users.** `set_enabled(install_id, False)` already refused on `scope='required'` (M2). `uninstall()` had no equivalent check at all — a required install could be deleted outright even though it couldn't be merely disabled, which defeats the point of "required." Fixed: `uninstall()` now raises the same way `set_enabled()` does when `scope='required'`. (Admin's `admin_disable_org_default()` above is a *different* action — an org-level policy change, not a per-install user action — and deliberately is not blocked by this.)

**(c) Concurrent first requests create no duplicates.** The real mechanism this relies on already exists and is already tested: the `UNIQUE NULLS NOT DISTINCT (item_id, org_id, installed_for)` constraint (task B-1) plus `install()`'s translation of the resulting `IntegrityError` into a typed `ConflictError` (this file's own Edge cases, above). B-12's future `ensure_provisioned()`-style upsert will rely on the exact same constraint — whichever of two concurrent first-request callers loses the race gets a conflict (or, for an `INSERT ... ON CONFLICT DO NOTHING` shape specifically, a silent no-op) rather than a second row. Proven now, ahead of B-12, by firing `install()` for the identical `(item_id, org_id, installed_for)` from 10 real concurrent threads and asserting exactly one succeeds (`tests/services/ecosystem/test_installs_service_lifecycle.py::test_concurrent_first_installs_create_no_duplicates`) — this is the same DB-level guarantee B-12's own upsert will lean on, demonstrated against the exact mechanism rather than asserted from documentation alone.

**(d) Row-growth estimate and cleanup when users are deactivated.** Estimate: lazily-provisioned rows are bounded by `(active users) × (builtin items + org-provisioned-default items)` — not unbounded, since a user only ever gets at most one row per item (the same unique constraint from (c) prevents duplicates), and the set of builtin/org-default items is small and admin-curated, not user-generated. The actual growth-rate driver is user count, not usage. `installs_service.cleanup_installs_for_inactive_users(org_id=None, dry_run=True)` deletes `ecosystem_installs` rows whose `installed_for` matches a `users.is_active=false` row and whose `origin IN ('provisioned','required')` — deliberately narrow: user-created content (`origin='created'`) and rows shared by a still-active teammate (`origin='shared'`) are left alone, since only the mechanically-provisioned subset is dead weight once its owner is deactivated (never functionally harmful either way — no code path re-reads a stale row and does anything wrong with it — this is pure row-count hygiene). `dry_run=True` (the default) only counts; a caller passes `dry_run=False` to actually delete. **Not wired into `routers/scim_router.py`'s existing SCIM deprovisioning flow** (the thing that actually sets `users.is_active=false` today) — that would mean editing an existing, unrelated router (additive-only standing rule); this is a standalone maintenance utility a future scheduled job or admin action can call, not an automatic side effect of deactivation yet.

## Sequence diagrams
```
Auto-install (task E's hook, triggered by the gate — see LLD/gate.md):
    gate verdict resolves pass/warn, trigger ∈ {ui_add, chat_create}
        → installs_service.install(scope/origin per provision_scope mapping)

Require / unrequire (Review round following M1, item F):
    admin calls POST /ecosystem/items/{id}/require
        → policy_service.require_item(item_id, org_id)
        → UPDATE ecosystem_installs SET scope='required', origin='required'
          WHERE item_id=... AND org_id=... AND origin='provisioned'
        → future lazy-provisioning calls (task B-12) for not-yet-provisioned
          users in that org read this same origin='required' state
```

## Edge cases and errors
- **`uninstall` never touches `ecosystem_items`; `deprecate` never touches any other org's `ecosystem_installs` rows.** Verified directly: `uninstall()` operates only on the single install row by id; `deprecate` (in the router, since it needs a schema column `ecosystem_items` doesn't have — see below) only ever updates the one item row.
- **A second install of the same `(item_id, org_id, installed_for)` raises a typed `ConflictError`, not a silent duplicate** — enforced by the real `UNIQUE NULLS NOT DISTINCT` DB constraint from task B-1 (see `LLD/gate.md`'s Edge cases for the critical bug that made this constraint inert until this milestone found and fixed it), caught and re-raised as `installs_service.ConflictError` so the router never leaks a raw `IntegrityError`.
- **`scope='required'` installs can never be disabled or uninstalled by a user** — `set_enabled(install_id, False)` and (as of item 4b, pre-M3) `uninstall()` both raise rather than silently no-op'ing or succeeding, so a caller can't accidentally disable OR delete something the required-flag is supposed to prevent either way.
- **No `created_by`/owner column exists on `ecosystem_items`** — a real, disclosed schema gap found while implementing `deprecate` and `compute_allowed_actions`'s ownership checks. This milestone's `deprecate` endpoint enforces admin-only (`marketplace:admin_sources`) rather than "owner or admin," since there is currently no column to check ownership against. `compute_allowed_actions()` itself accepts `is_owner` as a caller-supplied boolean specifically so this gap doesn't block testing the function's own logic — whoever eventually adds the ownership column only needs to change how that one boolean is computed, not the action-computation logic itself.
- **Org policy CRUD (`GET`/`PUT /ecosystem/policy`) has no backing table.** `CONFIG_AND_PRODUCTS.md`'s `policy_summary` read shape was speced, but no `ecosystem_org_policy`-shaped write table was ever added to task B-1's DDL. Disclosed as a real gap for whichever future task needs this to actually persist anything — not built here.

## How to extend
**Plugins/Connectors/MCP servers reuse this exact path, unchanged** (Review round following M1, item E): upload → object storage (`store/ecosystem_object_storage.py`) → gate (`services/ecosystem/gate_service.py`'s orchestrator, stages per `ECOSYSTEM_PLAN.md` §6) → auto-install on `pass`/`warn` for `trigger ∈ {ui_add, chat_create}` (`installs_service.install()`, this file's own subject) → `ecosystem.changed` event (task B-13) → resolved into the caller's available surfaces (`resolver_service.get_effective_capabilities`, task B-11). Nothing about this pipeline is skill-specific — the type-specific parts are entirely upstream of it (manifest parsing differs per type in gate stage 1, and `mcp_connector_stage`/sandbox-stage specifics differ per type in stages 5-7) and downstream of it (how each type surfaces in chat/Agent Studio/desktop). When Plugins/MCP/Connectors flip from `coming_soon` to `available` (a config-only change, `CONTRACTS.md` §8), this install-lifecycle path requires no code change to accommodate them — it was built type-agnostic from the start via `ecosystem_items.item_type` and `ecosystem_installs`, not a skill-only table.

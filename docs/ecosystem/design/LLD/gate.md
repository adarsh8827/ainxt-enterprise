# LLD — Verification gate

**Purpose**: the automated pipeline every new or updated catalog item passes through before it's usable — manifest validation, license enforcement, static safety scanning, supply-chain checks, a hardened sandbox stage, and an ethics/policy review. Landed in tasks B-8/B-9 (M2).

## Files / functions
- `services/ecosystem/gate_service.py` — the orchestrator (`enqueue_gate_run()`, `run_gate()`). Called "gate_orchestrator.py" in the phase plan's prose; kept as `gate_service.py` since that's the file task B-3 already established for this role. As of item 2 (pre-M3), `enqueue_gate_run()` only creates the `ecosystem_gate_runs` row and enqueues to `ecosystem_gate_queue` (`core/job_queue.py`'s `enqueue_ecosystem_gate_job()`) — it does not call `run_gate()` itself. `run_gate()` is the function that actually executes all 7 stages; only `workers/ecosystem_gate_worker.py` calls it in production.
- `workers/ecosystem_gate_worker.py` — the dedicated gate-worker's RQ entry point (`run_ecosystem_gate_job()`), unpacking the queue payload and calling `gate_service.run_gate()`. This is the **only** process in production that ever calls `run_gate()`, and the only one docker-compose.yml grants Docker socket access to for this purpose.
- `core/job_queue.py` — `Q_ECOSYSTEM_GATE` ("ecosystem_gate_queue") queue constant and `enqueue_ecosystem_gate_job()` convenience wrapper, following the exact same pattern as `enqueue_security_scan_job()`/`enqueue_codewiki_job()`. No thread fallback if Redis/rq is unavailable (this module's platform-wide, pre-existing convention). **Task B-6 update**: the RQ job id is now deterministic (`ecosystem_gate_job_id(gate_run_id)` → `"ecosystem_gate_<gate_run_id>"`, underscore), not a random UUID, so a gate run's real in-flight status can be looked up by `gate_run_id` alone — see the sweeper below for why that matters. **Real bug, found and fixed the same day**: this originally used a colon (`"ecosystem_gate:<gate_run_id>"`), which RQ's own job-id validation rejects — every enqueue silently failed (caught by the enqueue-resilience fix below, which left the row `pending` for the sweeper), and the sweeper's own retry computed the identical invalid id, so it could never recover. Fixed to underscore; see `CHANGELOG.md`'s dated entry.
- `services/ecosystem/gate/manifest_stage.py` — stage 1: name/description validation, bundle file-count/size caps, path-traversal defense-in-depth.
- `services/ecosystem/gate/license_stage.py` — stage 2: pass/block by default (task mandate, unconditional for every existing caller). Checks the item's own license plus an optional `dependencies` list (unused by skills this phase, present for forward compatibility). **Task C's tiered license policy** (`ECOSYSTEM_PLAN.md` §11.2) adds a `relaxed: bool = False` kwarg — never a default, only ever set by `run_gate()` when the gate run's own `license_tier` column (below) is `'relaxed'` — which turns a disallowed OWN license (never a dependency's) into a `warn`-severity `LICENSE_WARNING_PRIVATE_SCOPE` finding instead of a `block`-severity `LICENSE_NOT_ALLOWED` one.
- `services/ecosystem/gate/static_safety_stage.py` — stage 3: wraps `agents/compliance_engine.py`'s `analyze()`, filtered to `category ∈ {"SECRET", "KEY"}` — see Edge cases below for why this is filtered by `category`, not the more granular `type` field the original task text named.
- `services/ecosystem/gate/supply_chain_stage.py` — stage 4: pinned-version check on an optional `dependencies` list; no malicious-hash lookup exists yet (disclosed gap, no such database exists in this codebase).
- `services/ecosystem/gate/sandbox_stage.py` — stage 5: Python `ast.parse()` import-allowlist check, plus an optional test-entrypoint execution via `sandbox/ecosystem_gate_executor.py`.
- `sandbox/ecosystem_gate_executor.py` — `EcosystemGateExecutor`, extends `sandbox/docker_executor.py`'s `DockerExecutor`, overriding `_run()` entirely (the base class doesn't parameterize `read_only`/timeout/mem, so subclassing and overriding is the only way to change them) for `network_disabled=True` unconditionally, `read_only=True` rootfs, a tmpfs-backed `/sandbox` (code enters the container via its command line, base64-encoded, never a host bind mount), and a longer timeout/lower memory profile than the base class's short-snippet defaults. As of item 2 (pre-M3), `_run()` also calls `_assert_gate_worker_process()` as its very first line, before any container setup — see "Deployment: the gate-worker process" below.
- `services/ecosystem/gate/ethics_stage.py` — stage 6: a fresh-context call via `models/model_router.py`'s `model_router.generate()`. Never raises (per that module's own contract); failure is signaled by the returned text starting with `"Error"`, treated identically to an unparseable response — both resolve to `pending` with a retry, never `pass`.
- `services/ecosystem/gate/mcp_connector_stage.py` — stage 7: always-pass no-op for `item_type=skill`.
- `services/ecosystem/gate/types.py` — the shared `Finding`/`StageResult` dataclasses every stage returns.

### Fast path for private, self-created, no-script skills (task D)

`services/ecosystem/gate_service.py`'s `run_fast_path_gate()` — a synchronous alternative to `enqueue_gate_run()`, called only by `create_service.create_via_write()` (covers Write, Create with AI, and Save as skill, all three of which submit through this same function) when `provision_scope` resolves private, `item_type == "skill"`, and there are no bundled files. Runs only **stage 1 (manifest)** and **stage 3 (static_safety** — now also covering a hidden-text/prompt-injection heuristic, see below) in-process; skips license/supply_chain/sandbox/ethics/mcp_connector entirely (license was already resolved by `_resolve_creation_license()`'s Tier 3 self-authored/acknowledged path — re-deriving it via `license_stage.run()` would just re-block an already-approved license). Writes the same `ecosystem_gate_runs`/`ecosystem_gate_findings`/`ecosystem_item_versions.gate_verdict` rows `run_gate()` would, just resolved immediately — `scanner_version` is tagged with the `"fast-path-private"` marker so a later scope-widen can tell a fast-pathed version apart from a fully-gated one. Pass/warn auto-installs the creator synchronously (same `_auto_install()` helper `run_gate()` uses for `_AUTO_INSTALL_TRIGGERS`); fail leaves the item created but blocked, same shape the async path already produces for a fail verdict, just without the wait. Uploads and imports never take this path, regardless of scope — `_create_item_and_version()`'s `attempt_fast_path` flag is only ever `True` from `create_via_write()`.

`static_safety_stage.py`'s hidden-text/prompt-injection scan (`_scan_hidden_text_and_injection()`) is a static, regex/Unicode-category check — no model call, so it's safe to run synchronously in the fast path — for Unicode format-category (`Cf`) characters (zero-width space/joiner, BOM, bidi overrides) and a short curated list of known injection phrases ("ignore all previous instructions," etc.). Always runs regardless of `COMPLIANCE_SERVICE_ENABLED`, unlike the secret/key scan in the same stage, since it has no external dependency; a disclosed, deliberate first-pass heuristic, not a claim of catching every technique.

`gate_service.ensure_full_gate_for_scope_widen(item_id, version_id, ...)` — the other half: called from `policy_service.share()` and the install-scope-widen check in `routers/ecosystem_router.py`'s `install_item` (any scope beyond `private`: shared/org/provisioned/required). No-op if the version's latest gate run wasn't fast-pathed (already fully gated, nothing to upgrade). Otherwise: resets `gate_verdict` to `'pending'` synchronously in the same call, then enqueues a real, full `enqueue_gate_run()` with `trigger="admin_provision"` (reused across every scope-widen case rather than adding a new trigger value to `ecosystem_gate_runs`' CHECK constraint for one narrow case) — so anything reading `latest_verdict` sees `pending`, never the stale fast-path `pass`, until that real run finishes.

## API and DB changes
No new tables (uses `ecosystem_gate_runs`/`ecosystem_gate_findings` from task B-1). `ecosystem_item_versions.gate_verdict` is updated in place once a run resolves. **Task C** (`db/migrate.py`'s Part AD6) adds `ecosystem_gate_runs.license_tier` (`VARCHAR(10) NOT NULL DEFAULT 'strict'`) — set by `services/ecosystem/create_service.py`'s `enqueue_gate_run(..., license_tier=...)` call, read back by `run_gate()` to decide `license_stage.run()`'s `relaxed` kwarg. Also adds `ecosystem_org_policy.allowed_licenses_shared` (JSONB, default `["MIT", "Apache-2.0"]`) — unrelated to a specific gate run, checked synchronously by `policy_service.py`/`create_service.py` at share/install/creation time, never by the gate pipeline itself.

## Deployment: the gate-worker process (item 2, pre-M3)

**The Docker socket is root-equivalent host access** — any process that can reach it can launch a privileged container, bind-mount the host filesystem, or otherwise escape its own confinement entirely. The gate's sandbox stage (`sandbox_stage.py`'s optional test-entrypoint execution, `sandbox/ecosystem_gate_executor.py`) is the only part of this gate that touches Docker, so it is the only part of this initiative that has any business running where the socket is reachable.

Two independent layers enforce that the gateway process never runs this code, not one:

1. **No in-process call path exists.** `enqueue_gate_run()` (called from `create_service.py`, `scripts/ecosystem/backfill_legacy_items.py`, `scripts/ecosystem/seed_builtin_skills.py` — all of which can run inside the gateway process or a one-off script) only enqueues; it never calls `run_gate()` directly. `run_gate()` is only ever called from `workers/ecosystem_gate_worker.py`, which only ever runs as `docker-compose.yml`'s dedicated `gate-worker` service (`python workers/start_workers.py --gate`).
2. **A fail-closed runtime guard, in case the first layer is ever bypassed** (a future caller mistakenly imports and calls `run_gate()` directly, a misconfigured deployment runs `workers/start_workers.py` with no flags in a container that happens to have Docker access, etc.). `sandbox/ecosystem_gate_executor.py`'s `EcosystemGateExecutor._run()` calls `_assert_gate_worker_process()` as its first line, before any container setup: it raises `EcosystemGateProcessNotAllowedError` unless the process's own environment has `ECOSYSTEM_GATE_SANDBOX_ALLOWED=true` set. This is a **fail-closed allow-list, not a "detect the gateway and block it" heuristic** — only `docker-compose.yml`'s `gate-worker` service sets this env var; every other process (the gateway included, even though it happens to have its own, unrelated `docker.sock` mount — see below) is refused by default, with no code trying to guess "am I the gateway" and risking getting it wrong. `services/ecosystem/gate/sandbox_stage.py`'s `run()` catches this specific exception and converts it into a `block`-severity `SANDBOX_NOT_ALLOWED_HERE` finding (failing the item) rather than letting it crash the calling process — a misconfiguration must never silently pass an unverified item, and must never take down whatever process hit it either.

**Disclosed, out-of-scope finding**: `docker-compose.yml`'s `gateway` service has its own, pre-existing `/var/run/docker.sock` mount, unrelated to this initiative — it predates the ecosystem marketplace and exists for the doc-generation pipeline's sandbox health check and `docker_executor.py`'s SDK-path optimization (see that service's own comment). This task does not remove it: doing so would be an out-of-scope change to an unrelated, working feature (strict-scope standing rule). What this task *does* guarantee is that the ecosystem gate's own sandbox code never runs there even though the socket happens to be reachable — enforced by the two layers above, not by assuming the mount will someday be removed. Tracked as a named security follow-up (not fixed here) in `docs/ecosystem/CONFIG_AND_PRODUCTS.md` §11.

**`workers/start_workers.py --gate`** is the only pool that should ever consume `ecosystem_gate_queue`; the "no flags, all queues" dev-only mode also includes it (for a bare-metal dev machine that already has Docker + the allow-flag set) but is never used this way in `docker-compose.yml`. `install.sh` does not auto-start `gate-worker` (matching existing precedent — `security-worker`/`connector-worker`/`coach-worker`/`scheduler` aren't auto-started either); start it manually with `docker compose up -d gate-worker` (`README.md`'s "Marketplace: starting the gate-worker" section documents this for operators). **`gate-sweeper` (new, 2026-09-28) must be started alongside it** (`docker compose up -d gate-worker gate-sweeper`) — without it, a stuck/orphaned gate run has nothing to detect and re-enqueue it; see the health-signal and sweeper sections below for why it's a separate service rather than a thread inside `gate-worker`.

### Gate-worker health signal (item 2's follow-up, pre-M3; liveness source rewritten 2026-09-28)

A pending gate run has no way to tell "still verifying" apart from "no worker has ever picked this up" without an explicit health signal — the whole point of a dedicated gate-worker is that it can simply not be running. `services/ecosystem/gate_health_service.py`:

- **Liveness** used to be a hand-rolled Redis heartbeat key, written every `HEARTBEAT_INTERVAL_SECONDS` (30s) by a background thread the `gate-worker` process started on boot (`_gate_heartbeat_thread()`). **Real incident, 2026-09-28**: that thread ran in the SAME top-level process that also forks an RQ work-horse per job — a fork landing while the thread held the DB connection pool's own lock left the forked child deadlocked on it forever (`os.fork()` only duplicates the calling thread, not the one holding the lock), and every job hit RQ's blunt 450s job timeout instead of ever completing. `docker exec`'d process inspection (`/proc/<pid>/wchan` showing `futex_do_wait`, shared socket inodes across sibling work-horses) confirmed this directly — see `CHANGELOG.md`'s dated entry for the full account. **Fix**: the heartbeat thread is gone; `get_health()` now calls `core/job_queue.py`'s `get_queue_worker_liveness(Q_ECOSYSTEM_GATE)`, which reads RQ's *own* worker registry (`rq.Worker.all()`, kept alive by RQ itself with no thread of ours needed) — no custom key, no thread, no pre-fork connection.
- **`get_health()`** — the read side: whether any RQ worker is currently registered on `ecosystem_gate_queue`, plus a count of `ecosystem_gate_runs` rows that are `verdict='pending'`, `finished_at IS NULL`, and `started_at` older than `STUCK_VERIFYING_THRESHOLD_SECONDS` (600s — generous relative to the sandbox stage's own 120s `GATE_EXECUTION_TIMEOUT`, so a run that's actually still processing is never misreported as stuck). Returns a human-readable `message` when either no worker is registered or stuck runs exist; `None` when healthy. Never raises — a Redis/DB hiccup degrades to reporting unhealthy rather than breaking whatever admin surface calls it.
- **`GET /ecosystem/admin/gate-health`** (`routers/ecosystem_router.py`, gated by `marketplace:admin_sources`) — a standalone admin endpoint exposing `get_health()` directly. Not yet folded into `GET /ecosystem/config` (task B-12/M3 — that endpoint doesn't exist yet); this is the interim admin-visible signal until it does.
- **`GET /ecosystem/jobs/{job_id}`** now returns a `stuck_message` field (`null` when not applicable) when that specific run is itself past the stuck threshold, pointing the caller back at the admin check above — so a caller polling one item's status gets a clear signal without having separate admin access.

Tests: `tests/services/ecosystem/test_gate_health_service.py` — the two heartbeat-key tests were replaced with RQ-registry-based equivalents (mocked unhealthy/healthy, plus a real `Worker.register_birth()`/`register_death()` round trip against real Redis), see the sweeper section below for the rest.

### Stuck-run sweeper (task B-6 — "gate jobs occasionally never picked up")

**Root cause**: `enqueue_gate_run()` always committed its `ecosystem_gate_runs` row *before* calling `enqueue_ecosystem_gate_job()` — the correct order (a job is never enqueued without a backing row) — but a transient failure in that second call (the queue hitting its 200-item depth limit, `core/job_queue.py`'s `_QUEUE_DEPTH_LIMITS`; or a Redis connection blip) used to propagate straight out of `enqueue_gate_run()` as an exception. By then the row already existed, committed, at `verdict='pending'` — with no RQ job ever created for it, and no way to recreate one, since the auto-install/version-bump context (`installed_by`/`installed_for`/`org_id`/`surfaces`/`provision_scope`) only ever lived inside that (never-created) job's payload. The caller (e.g. `create_via_write()`) would also see its otherwise-successful item creation raise — a confusing double failure for what was, from the item/version's point of view, a successful creation.

**Fix, two parts:**
1. `db/migrate.py`'s **Part AD5** adds `installed_by`/`installed_for`/`org_id`/`surfaces`/`provision_scope`/`swept_at` columns to `ecosystem_gate_runs` (all nullable/additive — existing rows read back `NULL`, no behavior change for any existing query). `enqueue_gate_run()` now persists this context onto the row in the same commit that creates it, and its RQ-enqueue call is wrapped in a `try`/`except` that logs and swallows a failure instead of re-raising — the row is left `pending`, recoverable, and the caller's item/version creation is never falsely reported as failed.
2. `services/ecosystem/gate_health_service.py`'s **`sweep_stuck_gate_runs()`** — finds rows `verdict='pending'`, `finished_at IS NULL`, `started_at` older than `STUCK_VERIFYING_THRESHOLD_SECONDS`, and not already swept within the last `STUCK_VERIFYING_THRESHOLD_SECONDS` (`swept_at` cooldown, so a genuinely slow-but-fine run doesn't get re-enqueued on every tick). For each, it checks the RQ job's real status by its now-deterministic id (`core.job_queue.get_job_status(ecosystem_gate_job_id(run.id))`) — if it's actually `queued`/`started`/`deferred`/`scheduled`, it's genuinely in flight and is left alone (`still_in_flight` count); otherwise it's re-enqueued using the row's **own** persisted columns (never the original, long-gone caller's arguments), and `swept_at` is stamped, with `sweep_attempts` incremented (see below). Never raises — a DB/Redis hiccup here degrades to a no-op sweep, not a crashed worker process.
3. **Runs as its own dedicated process (rewritten 2026-09-28)**: `workers/start_workers.py --gate-sweeper` (a new, additive `docker-compose.yml` service, `gate-sweeper`) runs `_run_gate_sweeper_loop()` as the entire body of that process, ticking every `HEARTBEAT_INTERVAL_SECONDS` (30s). It used to run as a second daemon thread inside the `--gate` process itself, alongside the heartbeat thread — that was the actual root cause of the fork-lock deadlock described in the health-signal section above (this thread's own `SessionLocal()` calls were the lock a work-horse fork could land on). `--gate` and `--gate-sweeper` are deliberately mutually exclusive: the former only forks work-horses, the latter only sweeps, and neither shares a process with the other.
4. `get_health()` now also returns `last_sweep` (the most recent sweep's `{checked, reenqueued, still_in_flight, permanently_failed, reenqueued_gate_run_ids, permanently_failed_gate_run_ids, swept_at}`, persisted to Redis the same way the old heartbeat was) — admin-visible via the existing `GET /ecosystem/admin/gate-health` endpoint, no new route needed.
5. **Retry/backoff + max-attempts (real incident, 2026-09-28)**: `ecosystem_gate_runs.sweep_attempts` (`db/migrate.py` Part AD10) tracks how many times a row has been swept. `_resweep_cooldown_for(attempts)` doubles the cooldown per attempt (capped at 1 hour). Past `_MAX_SWEEP_ATTEMPTS` (3), the sweeper stops retrying and calls `_mark_permanently_failed()`, resolving the run to `verdict="fail"` with a `GATE_WORKER_INTERRUPTED` finding instead of retrying a genuinely-broken row forever.

Tests (`tests/services/ecosystem/test_gate_health_service.py`): a run with no RQ job in flight is re-enqueued using its own persisted context; a run genuinely still queued/running is never touched; a row already swept within the cooldown is skipped entirely; a run whose RQ job was marked `failed` by a killed work-horse is still treated as safe to retry; backoff cooldown grows exponentially and is respected per-row; exceeding max attempts marks the run permanently failed with a real finding; `get_health()` surfaces the `last_sweep` summary; the sweeper loop re-enqueues an orphaned job when run as the body of its own process (not a thread); and a deterministic fork+lock deadlock reproduction (holds the pool's own mutex, forks, proves the child hangs without the `os.register_at_fork` fix in `db/database.py`/`core/kv/queue.py` and succeeds with it). `tests/services/ecosystem/test_gate_enqueue_resilience.py` (3 tests) reproduces the enqueue-failure race directly: `enqueue_gate_run()` survives a forced RQ-enqueue failure (does not raise); the row it leaves behind carries the full recovery context; a failure in the DB commit itself (as opposed to the RQ enqueue) still correctly raises, since no row — and therefore nothing for the sweeper to ever find — was created at all.

## Edge cases and errors
- **Ethics reviewer unavailable, or its response can't be parsed into a verdict → `pending` + implicit retry-on-next-call, never `pass`.** This is the M0-review correction, and it applies identically whether the caller is a normal creation (B-6), the legacy backfill (B-4), or builtin seeding (B-22) — verified by a dedicated test for each. There is no separate "retry job" yet (no async queue exists, see the module's own scope-limitation note) — a "retry" concretely means re-running `enqueue_gate_run`/`run_gate` again later, which produces a fresh attempt against the same content.
- **License stage failing is unconditional and independent of everything else** — even a cache hit or an otherwise-clean sandbox/ethics result never overrides a license `fail`. Enforced by `_aggregate()` checking `license` first, before even looking at `pending`. **Unchanged by task C's `relaxed` kwarg** — a relaxed-but-disallowed license produces `warn`, not `fail`, so `_aggregate()`'s own `license == "fail"` check simply never fires for it; a relaxed run's disallowed DEPENDENCY still blocks (relaxation is scoped to the item's own license only), and `_aggregate()` needed no changes at all to support this correctly.
- **`static_safety_stage` filters by `category`, not the exact `type` strings the original task text named** (SECRET/API_KEY/ACCESS_TOKEN/PRIVATE_KEY_LEAK/CERTIFICATE_LEAK/SSH_KEY_LEAK/KEY_ASSIGNMENT_LEAK). Verified directly against `agents/compliance_engine.py`'s actual output: `detect_secrets()` tags findings `AWS_KEY`/`JWT_TOKEN`/`API_KEY`/`BEARER_TOKEN`/`STRIPE_KEY`/`PRIVATE_KEY` under `category="SECRET"`; `detect_key_leaks()` tags `PRIVATE_KEY_LEAK`/`CERTIFICATE_LEAK`/`SSH_KEY_LEAK`/`KEY_ASSIGNMENT_LEAK` under `category="KEY"`. Filtering on category (`{"SECRET", "KEY"}`) captures the full, correct set the task actually intends without depending on exact "type" spellings that don't all match what the detectors currently emit.
- **This gate stage's efficacy depends on a pre-existing, unrelated flag: `COMPLIANCE_SERVICE_ENABLED` (`core/config.py`, default `false`).** `agents/compliance_engine.py`'s `analyze()` returns `[]` unconditionally when this flag is off (`agents/compliance_engine.py:410-412`, checked via the singleton's `.enabled`, itself class-bound at `agents/compliance_engine.py:167`). This task does **not** flip that flag's default (doing so would be an out-of-scope side effect on an unrelated, pre-existing feature this initiative doesn't own) — a deployment that wants the marketplace's static-safety stage to actually catch anything must set `COMPLIANCE_SERVICE_ENABLED=true` independently.
  **Fail-closed fix (pre-M3 follow-up to item 3)**: `static_safety_stage.run()` used to have no way to tell "scanned and found nothing" apart from "never scanned at all" — both produced empty findings and an implicit `pass`. It now checks `compliance_engine.enabled` first (`services/ecosystem/gate/static_safety_stage.py`) and returns `verdict="pending"` with an info-severity `SCANNER_UNAVAILABLE` finding when it's off, mirroring `ethics_stage.py`'s own `REVIEWER_UNAVAILABLE`/pending pattern exactly — an unscanned item can never resolve to `pass` by looking identical to a clean one. `tests/services/ecosystem/gate/test_static_safety_stage.py::test_scanner_disabled_resolves_to_pending_never_pass` proves it directly. A useful side effect: `tests/services/ecosystem/conftest.py`'s package-wide autouse fixture now forces `compliance_engine.enabled=True` for every test in this package (previously only `test_static_safety_stage.py` did this for itself) — this closed a real, previously-disclosed test-environment gap where `test_gate_service_orchestrator.py`'s secret-detection tests failed in any environment (including CI) that hadn't separately turned the flag on; they now pass unconditionally.
- **Confirmed and fixed in item 2's follow-up, item 3 (pre-M3)**: `static_safety_stage` depends on this dependency chain: `services/ecosystem/gate/static_safety_stage.py:41` calls `agents/compliance_engine.py`'s `analyze()` → `agents/compliance_engine.py:418` calls `detect_secrets(text)` → `agents/secret_detector.py`'s `detect_secrets()` (previously lines 203-244) never called its own `iter_env_secret_values()` helper (defined at line 165, and genuinely used elsewhere — `agents/redactor.py:129`'s output-redaction path — so "dead" specifically with respect to `detect_secrets()`, not dead code overall), despite that file's own comments describing exactly this fix for SNAKE_CASE env-var-assignment secrets (e.g. `AWS_SECRET_ACCESS_KEY=...`). Since the answer to "does static_safety depend on this path" was yes, fixed narrowly — one added block in `detect_secrets()` (`agents/secret_detector.py:236-244`) wiring in the existing, already-tested helper, nothing else in that file touched. Known, disclosed limitation: Python can't forcibly kill a running thread, so a timed-out stage's thread keeps executing in the background even after `run_gate()` gives up waiting on it — acceptable since the actual goal (the gate-worker's job queue never blocks past the timeout) is still achieved.

Measured ~44s cold on a dev machine — moved entirely to startup, never during a job's own timeout window again. `core/job_queue.py`'s `enqueue_ecosystem_gate_job()`'s own job-level `timeout` was bumped `300 → 450` — the old value was *less* than the sum of the per-stage timeouts above (390s worst case, every stage timing out in sequence), so RQ's blunt backstop could in principle have fired before the per-stage mechanism (the intended primary one) ever got a chance to resolve a run on its own terms.

## Catalog-checking round (2026-09-28) — proportionate gating, contract for the frontend

**Why**: a signed catalog item's bytes were already scanned once at crawl time (the crawler runs `static_safety_stage.run_fast_path()` before ever writing the pointer to the signed index) and an instructions-only skill has nothing for `supply_chain`/`sandbox` to check — running every stage unconditionally on every install was correct but wasteful. Nothing about the STAGE FUNCTIONS themselves changed; `run_gate()`'s orchestration now decides, per gate run, which stages to actually invoke vs. skip-with-a-recorded-reason.

### Item-state model (Discover card / `allowed_actions`)
No new top-level "state" enum field was added — the existing signals already say everything a card needs, just read together:
- **Catalog item, not yet added**: `EcosystemItem.scope == "central_index"`, `latest_version == null` (no `EcosystemItemVersion` exists yet — `materialize_from_catalog()` hasn't run). `allowed_actions` contains `"install"`, never contains anything gate-related. Show **"Catalog checks passed" + "+ Add"** — never "Verifying" for this state, since no gate run exists to be verifying.
- **Adding (install in flight)**: a version now exists with `gate_verdict` still `"pending"` on the just-created `EcosystemGateRun` (`GET /ecosystem/items/{id}/gate-runs`, newest row). Show **"Verifying"** — `stage_timings` (below) gives the current step.
- **Active**: latest gate run's `verdict` is `"pass"` or `"warn"` and an `EcosystemInstall` row exists for the caller → item usable, "Active".
- **Blocked**: latest gate run's `verdict == "fail"` because of a real content finding (not a stage timeout) → "Blocked (reason)" — the reason is the highest-severity `EcosystemGateFinding.message` for that run.
- **Failed / Retry**: an install *attempt* whose gate run is stuck (`verdict == "pending"` well past when it should have resolved — `gate_health_service.get_health()` already flags this) or whose `materialize_from_catalog()` call itself raised (`CatalogContentDriftError`/`CatalogInstallNotSupportedError`/an import fetch error) before a gate run ever got created. **"Retry" must only ever be shown for this state — never for an untouched, not-yet-added catalog item** (that state has no failed attempt to retry; it has "+ Add").
- The one thing genuinely new for the frontend to read: `EcosystemOrgPolicy`'s `ethics_review_policy`/`gate_precheck_enabled`/`gate_precheck_cap_per_hour` on `GET`/`PUT /ecosystem/policy` (admin Policies screen only — not a per-item field).

### Verification tab — `stage_timings` shape (per `EcosystemGateRun`, `GET /ecosystem/items/{id}/gate-runs`)
Existing JSONB column, additive change only — every entry gained an optional `"reason"` key, present exactly when `"status": "skipped"`:
```json
{
  "manifest":      {"status": "pass",    "duration_ms": 12,  "started_at": "2026-09-28T18:00:00+00:00"},
  "license":       {"status": "pass",    "duration_ms": 8,   "started_at": "2026-09-28T18:00:00+00:00"},
  "static_safety": {"status": "skipped", "duration_ms": 0,   "started_at": null, "reason": "signed catalog hash matched the crawled index -- CI already scanned these exact bytes at crawl time"},
  "supply_chain":  {"status": "skipped", "duration_ms": 0,   "started_at": null, "reason": "no scripts or dependencies declared -- nothing for this stage to check"},
  "sandbox":       {"status": "skipped", "duration_ms": 0,   "started_at": null, "reason": "no scripts or dependencies declared -- nothing for this stage to execute"},
  "ethics":        {"status": "skipped", "duration_ms": 0,   "started_at": null, "reason": "org ethics_review_policy='scripts_or_noncatalog' -- not required for this item"},
  "mcp_connector":  {"status": "pass",   "duration_ms": 3,   "started_at": "2026-09-28T18:00:01+00:00"}
}
```
- `"status"` values: `"pass" | "warn" | "fail" | "pending" | "skipped"` — unchanged set, `"skipped"` is not new (the pre-existing cache-hit/already-failed paths used it too) but now always carries a `"reason"`; the two pre-existing skip paths (`cached_verdict`/`already_failed`) were also given a `"reason"` string in this same round, so **every** `"skipped"` entry a client encounters from now on has one — no need to handle a skipped-without-reason case for new runs (old, pre-this-round rows in the DB won't have it; treat a missing `"reason"` as `null`/"no reason recorded").
- One query renders the whole tab: `stage_timings` is a single JSONB column on the one `EcosystemGateRun` row already being fetched — no N+1, unchanged from before this round.
- "In progress" polling/live-update mechanism (the existing event stream) is unchanged; this round only changed what ends up written into the column, not how it's read or pushed.
- Not-added state's "what CI checked" data (license/evidence, fast-scan result, crawl date) comes from `EcosystemItem.catalog_pointer` (`license_evidence`, `crawled_at` — already present, both set by the sync worker) — no gate run exists yet for this state, so there's nothing in `stage_timings` to show; render from `catalog_pointer` directly and say "Full check runs when you add it."

### Priority / retry / single-flight (backend-only, no new frontend-facing field)
`materialize_from_catalog()` takes a Redis lock (`core/kv`, key `ecosystem:gate:inflight:{item_id}:{version_id}`, short TTL) so two concurrent Adds of the same item collapse into one gate run — the second caller's HTTP response is identical either way (same `gate_run_id`), nothing for the frontend to special-case. Queue priority (`Q_ECOSYSTEM_GATE_HIGH`/`Q_ECOSYSTEM_GATE`/`Q_ECOSYSTEM_GATE_LOW`, `core/job_queue.py`) and the optional admin pre-check job are entirely server-side scheduling concerns — no response shape changed because of them.

### Ethics review policy values (admin Policies screen, `GET`/`PUT /ecosystem/policy`)
`ethics_review_policy: "always" | "scripts_or_noncatalog" | "never"` (default `"scripts_or_noncatalog"`). `gate_precheck_enabled: bool` (default `false`), `gate_precheck_cap_per_hour: int` (default `20`) — both currently backend-only settings with no admin UI wired to them yet (disclosed gap, not built this round); the fields exist on the policy object now so a future UI pass has somewhere real to read/write.

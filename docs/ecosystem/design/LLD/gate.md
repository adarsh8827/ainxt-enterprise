# LLD — Verification gate

**Purpose**: the automated pipeline every new or updated catalog item passes through before it's usable — manifest validation, license enforcement, static safety scanning, supply-chain checks, a hardened sandbox stage, and an ethics/policy review. Landed in tasks B-8/B-9 (M2).

## Files / functions
- `services/ecosystem/gate_service.py` — the orchestrator (`enqueue_gate_run()`, `run_gate()`). Called "gate_orchestrator.py" in the phase plan's prose; kept as `gate_service.py` since that's the file task B-3 already established for this role. As of item 2 (pre-M3), `enqueue_gate_run()` only creates the `ecosystem_gate_runs` row and enqueues to `ecosystem_gate_queue` (`core/job_queue.py`'s `enqueue_ecosystem_gate_job()`) — it does not call `run_gate()` itself. `run_gate()` is the function that actually executes all 7 stages; only `workers/ecosystem_gate_worker.py` calls it in production.
- `workers/ecosystem_gate_worker.py` — the dedicated gate-worker's RQ entry point (`run_ecosystem_gate_job()`), unpacking the queue payload and calling `gate_service.run_gate()`. This is the **only** process in production that ever calls `run_gate()`, and the only one docker-compose.yml grants Docker socket access to for this purpose.
- `core/job_queue.py` — `Q_ECOSYSTEM_GATE` ("ecosystem_gate_queue") queue constant and `enqueue_ecosystem_gate_job()` convenience wrapper, following the exact same pattern as `enqueue_security_scan_job()`/`enqueue_codewiki_job()`. No thread fallback if Redis/rq is unavailable (this module's platform-wide, pre-existing convention) — `enqueue_gate_run()` raises, leaving the just-created `gate_runs` row at `pending` for a later retry.
- `services/ecosystem/gate/manifest_stage.py` — stage 1: name/description validation, bundle file-count/size caps, path-traversal defense-in-depth.
- `services/ecosystem/gate/license_stage.py` — stage 2: pass/block only, no warn tier. Checks the item's own license plus an optional `dependencies` list (unused by skills this phase, present for forward compatibility).
- `services/ecosystem/gate/static_safety_stage.py` — stage 3: wraps `agents/compliance_engine.py`'s `analyze()`, filtered to `category ∈ {"SECRET", "KEY"}` — see Edge cases below for why this is filtered by `category`, not the more granular `type` field the original task text named.
- `services/ecosystem/gate/supply_chain_stage.py` — stage 4: pinned-version check on an optional `dependencies` list; no malicious-hash lookup exists yet (disclosed gap, no such database exists in this codebase).
- `services/ecosystem/gate/sandbox_stage.py` — stage 5: Python `ast.parse()` import-allowlist check, plus an optional test-entrypoint execution via `sandbox/ecosystem_gate_executor.py`.
- `sandbox/ecosystem_gate_executor.py` — `EcosystemGateExecutor`, extends `sandbox/docker_executor.py`'s `DockerExecutor`, overriding `_run()` entirely (the base class doesn't parameterize `read_only`/timeout/mem, so subclassing and overriding is the only way to change them) for `network_disabled=True` unconditionally, `read_only=True` rootfs, a tmpfs-backed `/sandbox` (code enters the container via its command line, base64-encoded, never a host bind mount), and a longer timeout/lower memory profile than the base class's short-snippet defaults. As of item 2 (pre-M3), `_run()` also calls `_assert_gate_worker_process()` as its very first line, before any container setup — see "Deployment: the gate-worker process" below.
- `services/ecosystem/gate/ethics_stage.py` — stage 6: a fresh-context call via `models/model_router.py`'s `model_router.generate()`. Never raises (per that module's own contract); failure is signaled by the returned text starting with `"Error"`, treated identically to an unparseable response — both resolve to `pending` with a retry, never `pass`.
- `services/ecosystem/gate/mcp_connector_stage.py` — stage 7: always-pass no-op for `item_type=skill`.
- `services/ecosystem/gate/types.py` — the shared `Finding`/`StageResult` dataclasses every stage returns.

## API and DB changes
No new tables (uses `ecosystem_gate_runs`/`ecosystem_gate_findings` from task B-1). `ecosystem_item_versions.gate_verdict` is updated in place once a run resolves.

## Sequence diagrams
```
[gateway process, or any other caller — create_service.py, scripts/ecosystem/*.py]
enqueue_gate_run(version_id, trigger, [installed_by, installed_for, org_id, surfaces, provision_scope])
    → creates ecosystem_gate_runs row (verdict='pending')
    → enqueue_ecosystem_gate_job(gate_run_id, ...)   [core/job_queue.py, ecosystem_gate_queue]
    → returns gate_run_id immediately — row stays 'pending' until the worker below runs

[gate-worker process ONLY — docker-compose.yml's gate-worker service, workers/start_workers.py --gate]
workers/ecosystem_gate_worker.py's run_ecosystem_gate_job(payload)
    → run_gate(gate_run_id, ...)
        → decode version's object-storage content (manifest + files)
        → manifest_stage, license_stage, static_safety_stage, supply_chain_stage (always run)
        → if license/manifest already failed: stages 5-7 short-circuit to 'fail', sandbox never invoked
        → elif a resolved (content_hash, scanner_version) gate run already exists: reuse its verdict
          for stages 5-7 collectively, sandbox/ethics/mcp_connector never invoked
        → else: sandbox_stage, ethics_stage, mcp_connector_stage run for real
          (sandbox_stage's optional Docker execution first calls
          EcosystemGateExecutor._run()'s _assert_gate_worker_process() guard —
          see "Deployment: the gate-worker process" below)
        → aggregate all stage verdicts (license=fail wins unconditionally; else pending > fail > warn > pass)
        → write gate_runs.verdict, gate_findings rows, item_versions.gate_verdict
        → if trigger ∈ {ui_add, chat_create} and verdict ∈ {pass, warn}: auto-install the creator
          (task E's post-verdict hook, calls installs_service.install())
```

## Deployment: the gate-worker process (item 2, pre-M3)

**The Docker socket is root-equivalent host access** — any process that can reach it can launch a privileged container, bind-mount the host filesystem, or otherwise escape its own confinement entirely. The gate's sandbox stage (`sandbox_stage.py`'s optional test-entrypoint execution, `sandbox/ecosystem_gate_executor.py`) is the only part of this gate that touches Docker, so it is the only part of this initiative that has any business running where the socket is reachable.

Two independent layers enforce that the gateway process never runs this code, not one:

1. **No in-process call path exists.** `enqueue_gate_run()` (called from `create_service.py`, `scripts/ecosystem/backfill_legacy_items.py`, `scripts/ecosystem/seed_builtin_skills.py` — all of which can run inside the gateway process or a one-off script) only enqueues; it never calls `run_gate()` directly. `run_gate()` is only ever called from `workers/ecosystem_gate_worker.py`, which only ever runs as `docker-compose.yml`'s dedicated `gate-worker` service (`python workers/start_workers.py --gate`).
2. **A fail-closed runtime guard, in case the first layer is ever bypassed** (a future caller mistakenly imports and calls `run_gate()` directly, a misconfigured deployment runs `workers/start_workers.py` with no flags in a container that happens to have Docker access, etc.). `sandbox/ecosystem_gate_executor.py`'s `EcosystemGateExecutor._run()` calls `_assert_gate_worker_process()` as its first line, before any container setup: it raises `EcosystemGateProcessNotAllowedError` unless the process's own environment has `ECOSYSTEM_GATE_SANDBOX_ALLOWED=true` set. This is a **fail-closed allow-list, not a "detect the gateway and block it" heuristic** — only `docker-compose.yml`'s `gate-worker` service sets this env var; every other process (the gateway included, even though it happens to have its own, unrelated `docker.sock` mount — see below) is refused by default, with no code trying to guess "am I the gateway" and risking getting it wrong. `services/ecosystem/gate/sandbox_stage.py`'s `run()` catches this specific exception and converts it into a `block`-severity `SANDBOX_NOT_ALLOWED_HERE` finding (failing the item) rather than letting it crash the calling process — a misconfiguration must never silently pass an unverified item, and must never take down whatever process hit it either.

**Disclosed, out-of-scope finding**: `docker-compose.yml`'s `gateway` service has its own, pre-existing `/var/run/docker.sock` mount, unrelated to this initiative — it predates the ecosystem marketplace and exists for the doc-generation pipeline's sandbox health check and `docker_executor.py`'s SDK-path optimization (see that service's own comment). This task does not remove it: doing so would be an out-of-scope change to an unrelated, working feature (strict-scope standing rule). What this task *does* guarantee is that the ecosystem gate's own sandbox code never runs there even though the socket happens to be reachable — enforced by the two layers above, not by assuming the mount will someday be removed.

**`workers/start_workers.py --gate`** is the only pool that should ever consume `ecosystem_gate_queue`; the "no flags, all queues" dev-only mode also includes it (for a bare-metal dev machine that already has Docker + the allow-flag set) but is never used this way in `docker-compose.yml`. `install.sh` does not auto-start `gate-worker` (matching existing precedent — `security-worker`/`connector-worker`/`coach-worker`/`scheduler` aren't auto-started either); start it manually with `docker compose up -d gate-worker`.

## Edge cases and errors
- **Ethics reviewer unavailable, or its response can't be parsed into a verdict → `pending` + implicit retry-on-next-call, never `pass`.** This is the M0-review correction, and it applies identically whether the caller is a normal creation (B-6), the legacy backfill (B-4), or builtin seeding (B-22) — verified by a dedicated test for each. There is no separate "retry job" yet (no async queue exists, see the module's own scope-limitation note) — a "retry" concretely means re-running `enqueue_gate_run`/`run_gate` again later, which produces a fresh attempt against the same content.
- **License stage failing is unconditional and independent of everything else** — even a cache hit or an otherwise-clean sandbox/ethics result never overrides a license `fail`. Enforced by `_aggregate()` checking `license` first, before even looking at `pending`.
- **`static_safety_stage` filters by `category`, not the exact `type` strings the original task text named** (SECRET/API_KEY/ACCESS_TOKEN/PRIVATE_KEY_LEAK/CERTIFICATE_LEAK/SSH_KEY_LEAK/KEY_ASSIGNMENT_LEAK). Verified directly against `agents/compliance_engine.py`'s actual output: `detect_secrets()` tags findings `AWS_KEY`/`JWT_TOKEN`/`API_KEY`/`BEARER_TOKEN`/`STRIPE_KEY`/`PRIVATE_KEY` under `category="SECRET"`; `detect_key_leaks()` tags `PRIVATE_KEY_LEAK`/`CERTIFICATE_LEAK`/`SSH_KEY_LEAK`/`KEY_ASSIGNMENT_LEAK` under `category="KEY"`. Filtering on category (`{"SECRET", "KEY"}`) captures the full, correct set the task actually intends without depending on exact "type" spellings that don't all match what the detectors currently emit.
- **This gate stage's efficacy depends on a pre-existing, unrelated flag: `COMPLIANCE_SERVICE_ENABLED` (`core/config.py`, default `false`).** `agents/compliance_engine.py`'s `analyze()` returns `[]` unconditionally when this flag is off — meaning `static_safety_stage` silently finds nothing and always passes in any deployment that hasn't separately turned this flag on. This task does **not** flip that flag (doing so would be an out-of-scope side effect on an unrelated, pre-existing feature this initiative doesn't own) — a deployment that wants the marketplace's static-safety stage to actually catch anything must set `COMPLIANCE_SERVICE_ENABLED=true` independently. Flagged prominently here and in the M2 milestone report rather than silently left for someone to discover later.
- **Pre-existing, unrelated bug found while testing this stage**: `agents/secret_detector.py`'s `detect_secrets()` never calls its own `iter_env_secret_values()` helper, despite that file's comments describing exactly this fix for SNAKE_CASE env-var-assignment secrets (e.g. `AWS_SECRET_ACCESS_KEY = "..."`) — such a value is silently never caught by `detect_secrets()` today. Out of scope to fix here (existing, unrelated code); this gate stage's own tests use a pattern the detector does catch (a bare `AKIA...` access-key-ID shape) instead of depending on the broken path.
- **A critical, previously-undetected bug in `db/migrate.py` was found and fixed while testing this task**: `Base.metadata.create_all()` (an early step in `run_migrations()`, pre-existing code) creates a bare version of every ORM-modeled table — including every `Ecosystem*` model added in this initiative — **before** task B-1's own raw-DDL `_part_ad1_...` runs. Since that raw DDL uses `CREATE TABLE IF NOT EXISTS`, `create_all()` winning the race made several of B-1's own constraints (`ecosystem_installs`' `UNIQUE NULLS NOT DISTINCT`, most notably) permanently inert on any database this ran against — the constraint text existed in the migration file but was **never actually applied**. Fixed by excluding every `ecosystem_*`/`oauth_*`/`credential_audit`/`desktop_devices` table from `create_all()`'s table list, mirroring the exact precedent already in that code for `document_embeddings`/`workspace_messages` (tables with their own raw-DDL migrations that `create_all()` must not preempt). See `docs/ecosystem/design/CHANGELOG.md`'s M2 entry for the full account, and `LLD/data-model.md` for what this means going forward (every future `Ecosystem*` ORM model must have its own corresponding raw DDL run **before** it can safely be exercised — `create_all()` alone is not sufficient and must never be relied on for these tables).

## Flags
None — the gate always runs in full; no per-stage disable switch exists anywhere (a built-in bypass would defeat the point).

## Tests
38 pure/near-pure unit tests across `tests/services/ecosystem/gate/` (one file per stage) plus 6 integration tests in `tests/services/ecosystem/test_gate_service_orchestrator.py` (real Postgres, ethics mocked for determinism) covering: a clean item passes; a secret-containing item warns/fails; ethics-unavailable resolves to pending; findings are recorded; a disallowed license short-circuits before ever invoking ethics; a content-hash cache hit skips re-invoking ethics entirely. These orchestrator/lifecycle tests exercise `run_gate()` through `tests/services/ecosystem/conftest.py`'s `_run_ecosystem_gate_inline` autouse fixture, which stands in for the real queue consumer (`workers/ecosystem_gate_worker.py`) by calling it synchronously in the test process — no rq worker runs during pytest. `sandbox_stage`'s test-entrypoint-execution tests run against a real Docker container (network isolation, exit-code propagation, and a genuine failure case all verified against the actual sandboxed process, not mocked); `tests/services/ecosystem/gate/conftest.py` sets `ECOSYSTEM_GATE_SANDBOX_ALLOWED=true` for this directory so they exercise real sandbox behavior rather than universally hitting the new refusal path.

**`tests/services/ecosystem/test_gate_queue_separation.py`** (6 tests, item 2/pre-M3) tests the queue separation itself, independent of stage logic: `workers/ecosystem_gate_worker.py` unpacks its payload into `run_gate()` correctly; `enqueue_gate_run()`, with the inline stub explicitly undone (restoring the real `core.job_queue.enqueue_ecosystem_gate_job`, captured at module-import time — restoring it via a fresh `from core.job_queue import ...` inside the test body would just re-read whatever the autouse fixture already patched it to), returns immediately with the row still `pending` (skips if Redis/rq isn't reachable); `EcosystemGateExecutor`'s `_assert_gate_worker_process()` refuses without the allow-flag and passes with it; `sandbox_stage.run()` converts a refusal into a `block` finding rather than crashing; `sandbox_stage.py` never imports anything Docker-related at module level (so importing `gate_service.py` — which the gateway process does, transitively — never requires Docker to be present).

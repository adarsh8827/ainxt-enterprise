# LLD — External sources catalog crawler (`services/ecosystem/catalog_crawler/`)

**Purpose**: builds the pointer-file catalog that will live on the `ecosystem-index` orphan branch (docs/ecosystem/EXTERNAL_SOURCES_PLAN.md). This LLD covers what's landed so far on `feature/ecosystem-external-sources`: the crawler itself, its three source adapters, signing, and the pointer/report schemas. **Not yet landed** (tracked in the plan doc, not here): the instance-side sync worker (§5), install-from-catalog (§6), the admin Sources screen (§8), live search (§10), and the actual `ecosystem-index` branch + its GitHub Actions workflow — those come after sources.yaml clears stop point 1.

## Files / functions

- `services/ecosystem/catalog_crawler/pointer_schema.py` — `PointerEntry` (dataclass: namespace, item_type, display_name, description, category, tags, source_kind/url/ref/path, license_spdx/evidence, compatibility, content_hash, attribution, crawled_at, remote_only). `pointer_file_path()` returns `catalog/<item_type>/<publisher>/<name>.yaml`. `to_yaml_dict()`/`from_yaml_dict()` round-trip the on-disk YAML shape. `build_index_shards(entries)` groups entries by `item_type`, sorted by namespace, into the `index/<item_type>.json` shape.
- `services/ecosystem/catalog_crawler/sources_config.py` — parses `docs/ecosystem/catalog/sources.yaml` (the reviewed crawl allowlist) into `GithubRepoSource`/`GithubTopicSearchSource`/`WellKnownSource`/`McpRegistrySource`. `load_yanked(path)` reads `yanked.yaml`'s flat namespace list (missing file == nothing yanked). Read-only — this module never writes either file; changes go through a normal reviewed PR (plan §7).
- `services/ecosystem/catalog_crawler/crawl.py` — `run_crawl(sources_path, yanked_path, output_dir)`: for each enabled source, calls the matching adapter's discovery function, keeps only license-allowed candidates, runs `services/ecosystem/gate/static_safety_stage.py`'s `run_fast_path()` over the actually-fetched content as a crawl-time pre-filter (the full 7-stage gate still runs, unconditionally, at install time — this only screens out an obviously-bad candidate before it's ever written to the catalog), computes `content_hash` over the manifest text + bundled files, then writes one pointer YAML per surviving entry plus the sharded `index/*.json`. Filters out anything in `yanked.yaml` before writing. Returns a `CrawlReport`.
- `services/ecosystem/catalog_crawler/crawl_report.py` — `CrawlReport` (included/excluded lists), `excluded_by_reason()` (bucketed Counter), `to_markdown()`/`to_dict()` — the stop-point-2 artifact.
- `services/ecosystem/catalog_crawler/signing.py` — `sign_index_bytes(data)` / `verify_index_bytes(data, bundle_bytes, trusted_signer, *, allow_online_trust_root_refresh=False, trust_root_path=None)`, keyless Sigstore signing via the crawl workflow's own GitHub Actions OIDC identity (package: `sigstore==4.5.0`, Apache-2.0; imported lazily so this module loads fine without the package installed). `TrustedSigner(issuer, repository, workflow_name)` is what a verifier checks the signer against — matched via three separate X.509v3 certificate extensions Fulcio embeds (`OIDCIssuer`/`GitHubWorkflowRepository`/`GitHubWorkflowName`, combined with `AllOf`), deliberately **not** the branch ref (review decision, 2026-09-28, superseding an earlier issuer+subject/`Identity`-policy design: a ref-based match would break every time the workflow moves branches). `trusted_signer_from_env(value)` parses `ECOSYSTEM_CATALOG_TRUSTED_SIGNER`'s JSON string form (`{"issuer": "...", "repository": "owner/repo", "workflow_name": "..."}`), raising `ValueError` fail-closed on anything malformed/incomplete. A fork must configure its own signer (plan §2); there is no default that trusts every possible signer. Outside a CI job with an ambient OIDC credential, `sign_index_bytes()` raises `RuntimeError` by design (verified directly, not mocked, in `tests/services/ecosystem/catalog_crawler/test_signing.py`). **Verification is offline by default**: `TrustedRoot.from_file()` loads the pinned, checked-in `vendor/sigstore_trusted_root.json` (Sigstore's public production trust root, fetched once via a real TUF refresh, 2026-09-28) instead of fetching one over the network — confirmed directly against `sigstore-python` 4.5.0's own source that the resulting `verify_artifact()` call makes zero network requests (its `RekorClient` is constructed but never invoked given a bundle with an embedded inclusion proof, which every bundle `sign_index_bytes()` produces has). `allow_online_trust_root_refresh=True` is the one opt-in exception, contacting `tuf-repo-cdn.sigstore.dev`.
- `scripts/ecosystem/run_catalog_crawl.py`'s `--verify-after-sign` flag (requires `--sign`) immediately re-verifies each freshly-signed shard against `ECOSYSTEM_CATALOG_TRUSTED_SIGNER` (env var, required when the flag is set) before returning success — fail-closed: a signing bug producing a bundle this same process can't verify against its own trusted signer stops the job (nonzero exit) before the workflow's commit/push step ever runs, rather than being caught later by an installation's own sync worker. In `.github/workflows/ecosystem-catalog-crawl.yml`, the crawl job's own self-check value is built entirely from that run's ambient `github.repository`/`github.workflow` context (never hard-coded), so it's automatically correct on any fork and can never drift from the repo/workflow actually running the job.

## Adapter additions (additive, existing adapters untouched)

- `services/ecosystem/import_adapters/github_repo.py`'s new `search_repos_by_topic(topic, page=1)` — GitHub topic search, discovery-only: surfaces *candidate* repos for a human to add to `sources.yaml` via a reviewed PR. Never called by `crawl.py` itself (no source in `sources.yaml` currently enables it) — a discovery aid for maintainers, not part of the automated crawl path yet.
- `services/ecosystem/import_adapters/well_known.py`'s new `discover_skills_at_well_known(domain)` — lists every entry at a domain's modern-or-legacy index (mirrors `discover_skills_in_repo()`'s shape: one candidate dict per entry, license evidence + allow/deny verdict, nothing raised for a single entry's own failure). Includes the fetched `skill_md_text`/`files` on allowed candidates so the crawler can hash/fast-safety-check without a second fetch.
- `services/ecosystem/import_adapters/mcp_registry.py` (new file) — `list_servers(cursor=None)` / `discover_mcp_servers(max_pages=20)` against the official MCP Registry (`https://registry.modelcontextprotocol.io`, API v0.1). License comes from the entry's own npm/PyPI package metadata (fetched fresh from `registry.npmjs.org`/`pypi.org`'s JSON APIs), or an OCI package's explicit `licenses` annotation — never from the registry entry's own free-text fields. A server with no installable package (`remotes` only, no `packages`) is returned `remote_only=True, allowed=False` — catalog inclusion for those needs a human ToS review (plan §4), never automatic. **Corrected against the real, live API (2026-09-28, found during the first real crawl — this module's original version was a documented-but-unverified guess)**: every list entry wraps the actual server object under `"server"` (not flat), the pagination cursor is `metadata.nextCursor` (camelCase, not `next_cursor`), the registry returns one list entry per *published version* of a server (deduplicated here via `_meta."io.modelcontextprotocol.registry/official".isLatest`, or the same namespace appears more than once), and some PyPI packages put the full license *text* rather than a short identifier in `info.license` (now length-gated, falling back to the classifier scan for anything longer than a real identifier would be).

## Approval round additions (sources.yaml sign-off, before the first real crawl)

- `services/ecosystem/catalog_crawler/neutrality_check.py` (new) — `scan_for_ai_vendor_names(text)`, a flat, disclosed-as-heuristic list of real AI product/vendor names (word-boundary, case-insensitive). Called from `crawl.py`'s `_scan_all_content_for_vendor_names()` on every github_repo/well_known candidate's manifest + bundled files (not on mcp_registry entries, which have no fetchable content); a hit excludes the candidate with the matched name(s) in the reason.
- `sources_config.py`'s `GithubRepoSource` gained `include_paths`/`exclude_paths` (per-repo path scoping/exclusion), `needs_product`/`account_required` (become `needs-<product>`/`account-required` tags); `WellKnownSource` gained the same two tag fields plus `test_source` (tags the resulting `IncludedEntry.test_source`, and is disclosed in the crawl report, rather than counted as a real catalog contribution). A new `CrawlLimits` (`max_skills_per_repo` default 50, `max_total_items` default 10000) is parsed from `sources.yaml`'s top-level `crawl_limits:` block.
- `crawl.py` reworked: `_crawl_github_repo()` now scans every `include_paths` entry (or the whole repo if empty), drops any candidate under an `exclude_paths` subtree, and applies `_apply_per_source_cap()` (reports `CrawlReport.over_cap`, never silently truncates) to its own passing candidates before returning them. `_dedupe_by_content_hash()` runs once, across every source's combined output, preferring `github_repo` > `well_known` > `mcp_registry` for identical content (entries with no content_hash, i.e. `mcp_server` pointers, are never deduped against each other). `_check_circuit_breaker()` (ported from the reviewed teammate marketplace's own ingestion safeguard) compares each source's this-run content hashes against `_load_previous_hashes_by_source()`'s reading of a previously-built index (an optional `previous_index_dir` param, absent on a first crawl) and discards that source's results entirely if more than 20% of its previously-seen items changed. **`report.included` is now built once, at the very end of `run_crawl()`, from whatever entries actually survive yanking → dedup → the global cap** — no longer appended to speculatively inside each source's own crawl function, since a later step can still remove an entry a source itself thought was final.
- `crawl_report.py` gained `OverCapEntry`, `CircuitBreakerTrip`, and `IncludedEntry.test_source`.

## Rate-limit efficiency (found live during a rehearsal crawl, 2026-09-28)

`services/ecosystem/import_adapters/github_repo.py` gained, all additive, no change to any function's public return shape:
- `get_api_call_stats()`/`reset_api_call_stats()` — module-level counters: `total_requests` (every `_github_get()` call) and `rate_limit_consuming_requests` (excludes 304s, which GitHub's own documented behavior says do not count against the primary rate limit).
- `_github_get()` now sends `If-None-Match` from a per-path ETag cache (reusing the existing `fetch_cache.py` Redis backing, 24h TTL) and, on a 304, returns the cached body instead of making a fresh request count against the budget.
- `_fetch_text_file()` fetches from `raw.githubusercontent.com` directly instead of the Contents API — the single biggest source of rate-limit consumption the old implementation had (one API call per file: every SKILL.md, every conflict-scan file, every bundle file). `import_from_github()`'s own inline Contents-API call was replaced with a call to this same function, so both import paths now share one content-fetch implementation.
- `get_resolved_head_sha(repo, ref=None)` — two lightweight, ETag-cacheable calls (repo meta + commit lookup), no tree listing, no file fetch. Lets the crawler check "has this repo moved since the last crawl" cheaply.

`crawl.py`'s `_crawl_github_repo()` takes an optional `previous_repo_state` (built by `run_crawl()` from `_load_previous_rows_by_source()`/`_github_repo_state_from_rows()`, reading the previous crawl's own committed `index/*.json`): if the repo's current HEAD matches that state's recorded `resolved_sha`, the repo is skipped entirely — `discover_skills_in_repo()` and every per-skill import are never called at all — and its previous entries are reconstructed verbatim via `PointerEntry.from_yaml_dict()`. Recorded in `CrawlReport.skipped_unchanged_repos`. Real, disclosed limitation: if `sources.yaml`'s own config for that repo changed (a new `include_paths`/`needs_product`/etc.) since the last crawl, that change doesn't take effect until HEAD moves again. `run_crawl()` calls `github_repo.reset_api_call_stats()` at the start and records `github_repo.get_api_call_stats()` into `CrawlReport.api_call_stats` at the end, printed in `to_markdown()`.

## Reuse (per the plan's §12 reuse map — nothing here is a second implementation)

`crawl.py` calls `github_repo.discover_skills_in_repo()`/`import_from_github_path()`/`import_from_github()` and `well_known.discover_skills_at_well_known()` exactly as they already exist for the manual admin-import path (`LLD/external-import.md`) — the license-inheritance chain, SSRF guard, and fetch cache are all shared, not reimplemented. `services/ecosystem/compatibility.py`'s `classify_compatibility()` and `services/ecosystem/license_policy.py`'s `is_allowed_license()` are likewise the same functions the rest of the ecosystem service layer already uses.

## Open items before a real crawl can run

1. `docs/ecosystem/catalog/sources.yaml` needs sign-off (stop point 1).
2. The `ecosystem-index` orphan branch doesn't exist yet — created only after sign-off, from an empty tree (`git checkout --orphan`), never sharing history with `main`.
3. `.github/workflows/ecosystem-catalog-crawl.yml` (drafted, not yet run) checks out that branch, calls `crawl.run_crawl()`, signs the result, and commits back — needs `permissions: id-token: write` for `sign_index_bytes()`'s ambient OIDC credential to exist at all.
4. **`GITHUB_IMPORT_TOKEN` must be configured before a real crawl is useful.** A local rehearsal run (real network calls, run manually against `sources.yaml`, not via the actual workflow) hit GitHub's unauthenticated 60-requests/hour limit after scanning roughly one repo, rate-limiting every other `github_repos` source in the list. The crawl workflow needs this same instance-level credential the manual admin-import path already uses (`services/ecosystem/import_adapters/github_credential.py`) configured as a repo secret, or the vast majority of `sources.yaml`'s GitHub entries will fail with `discovery failed: ... rate-limited` every run.

### First rehearsal crawl (local, manual, real network — not yet the actual workflow) findings, 2026-09-28

Run once against the drafted `sources.yaml` to sanity-check the crawler end to end before committing to the real GitHub Actions workflow. Found and fixed four real bugs, all in `mcp_registry.py`/`pointer_schema.py` (documented above and in the LLD's own header comments); none in `github_repo.py`/`well_known.py`, which were already exercised by the manual admin-import path. With the rate-limiting above in effect, only 4 skill entries and 73 mcp_server entries actually landed in this run's `index/*.json` — not representative of what a token-authenticated crawl would produce, but useful as a real end-to-end proof the pipeline works: pointer YAML written, index JSON built, license/fast-safety gating applied (one real `PROMPT_INJECTION_PATTERN` hit on `addyosmani/agent-skills#skills/browser-testing-with-devtools`, correctly excluded), one real digest mismatch on `docs.x.com` (upstream content changed since this module's own recorded fixtures were taken, correctly excluded rather than silently trusted).

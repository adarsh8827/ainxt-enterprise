# LLD — UI package

**Purpose**: the one shared component library rendering the marketplace for both products, consuming only a server-provided configuration document — no product name, item type, feature flag, or category is ever hardcoded in this package. Tasks F-1 through F-10, F-13 landed in this milestone (M4); F-11 (chat integration UI) and F-12 (workspace host example, this file's own section below) are M5.

**Real container build bug found and fixed (task B-5)**: the paragraph above described the intended fix but it was never actually applied — `@heroicons/react` was never added to `ai-ui/vite.config.js`'s `resolve.dedupe` array, and `ai-ui/Dockerfile` never `COPY`'d `packages/ecosystem-ui/src` into the build context at all. Root cause: this package's `src/` has no `node_modules` of its own in the production image (only source is copied, matching the `@abs`/AgentStudio pattern), and `ai-ui/node_modules` is a *sibling*, not an ancestor, of `/app/packages/ecosystem-ui/src` inside the image — Rollup's normal directory walk-up resolution for a bare `@heroicons/react/...` import from an ecosystem-ui source file never reaches it, so a real `docker build -f ai-ui/Dockerfile .` failed outright with "Rollup failed to resolve import". This never surfaced on the host dev server because `packages/ecosystem-ui` also has its own local `node_modules` there (a leftover of running `npm install` directly inside that package for its own Storybook/test setup), which *is* an ancestor of its own `src/` on disk — a difference between the host and container filesystem layouts that made the bug invisible outside a real container build. Fixed by (1) adding `COPY packages/ecosystem-ui/src /app/packages/ecosystem-ui/src` to the Dockerfile, matching the pre-existing `@abs` copy line, and (2) adding `'@heroicons/react'` to `vite.config.js`'s `dedupe` array so Rollup resolves it through `ai-ui/node_modules` (which already declares it) instead of walking up from the ecosystem-ui source file's own directory. Verified with a real `docker build -f ai-ui/Dockerfile .` (succeeds) and running the resulting image (container reports `healthy`, serves `/portal/` with the Marketplace bundle present in `app.*.js`).

## Edge cases and errors

- **`GET /ecosystem/items/{id}` never actually worked by namespace over real HTTP — found only by a genuine HTTP round-trip, not by any of this milestone's 263 prior-passing tests, all of which called the service layer directly.** Every real namespace is `publisher/name`-shaped; `Detail.tsx`'s real navigation flow (`routing.ts`'s `detailPath()`) always requests by namespace, URL-encoding the slash as `%2F` — which Starlette/uvicorn decode back into a literal `/` *before* route matching, so the route (a plain `{item_id}` path parameter) 404'd before ever reaching the handler. Fixed server-side (`routers/ecosystem_router.py`'s `{item_id:path}`, with the route reordered after its `GET` sub-routes so the greedy converter doesn't shadow them) — see `CHANGELOG.md`'s own dated entry for the full before/after `curl` evidence and the new router-level HTTP regression tests (`tests/services/ecosystem/test_ecosystem_router_http.py`). Recorded here because it's the reason this package's own `Detail.tsx` component test suite (which only ever exercises `MockEcosystemClient`, never real HTTP/routing behavior) could not have caught it — a reminder that this package's tests validate the *contract*, not the real router's URL-matching behavior, and the two need to be checked separately (which the M4 checkpoint's own "works against the real backend locally" step is what's actually for).
- **`EcosystemConfigProvider`'s `initialConfig` prop — a real bug found and fixed during this milestone's own component testing, not by code review alone.** An earlier draft had `Marketplace.tsx` receive an optional pre-fetched `config` prop but only use it for its own top-level loading gate, never actually feeding it into `EcosystemConfigProvider`'s context — every *descendant* screen (`Discover`, `Yours`, `CreateForm`, `UploadFlow`, `TypeTabs`, `AdminScreen`, ...) calls `useConfig()` directly, which reads from that same context, not from a prop. A host supplying a preset config would have left every one of those screens throwing "`useConfig()` called before `GET /ecosystem/config` resolved" the moment they rendered, since the provider's own internal state never learned about the preset value. Caught because `renderWithHost()` (the shared test helper) exercises exactly this path — every component test rendering a leaf screen directly (skipping `Marketplace.tsx`'s own loading gate) hit this immediately. Fixed by having `EcosystemConfigProvider` itself accept `initialConfig` and seed its state with it, skipping the fetch on the first render only (a `refetch()` call still always re-fetches for real).
- **`RouterHooks.basePath` — added after Detail.tsx's own Copy Link test caught a portability bug.** The first draft of `Detail.tsx`'s "Copy Link" handler hardcoded `/marketplace` as the URL prefix — correct for `ai-ui` (task F-2's actual mount point) but wrong for any other host, and this package is host-agnostic by design. `RouterHooks` gained an optional `basePath` field (default `""`) so a host declares its own mount point explicitly rather than this package assuming one.
- **`icon_url`'s `url:`/`emoji:` prefix + monogram fallback** (`CONTRACTS.md` §7): `ItemIcon.tsx` — the monogram's per-namespace color comes from `theme.color.monogramPalette` (a host-injected array), never a hardcoded hex array in the component; a namespace hash picks the index deterministically, verified as non-`undefined` at runtime with a thrown error (not a hardcoded fallback color) if a host somehow injects an empty palette.
- **`PUT` vs. `DELETE /ecosystem/featured/{item_id}` are NOT the same action** — a first draft of `AdminFeatured.tsx`/`EcosystemClient.setFeatured()` conflated "explicitly mark not-featured" (`PUT {featured:false}`) with "remove the org's override, revert to the platform default" (`DELETE`). Fixed by adding a distinct `clearFeaturedOverride()` method to the client interface, matching the two real, semantically-different backend endpoints.
- **No `@testing-library/react` auto-cleanup** — `test.globals` is deliberately `false` (matches this package's explicit-import convention throughout); RTL's own auto-cleanup only self-registers when it detects a *global* `afterEach`, so `src/test-setup.ts` registers `afterEach(() => cleanup())` explicitly. Without this, a second test in the same file reusing a `data-testid` query (e.g. two `KebabMenu` renders) fails with "multiple elements found," a real failure caught while writing this milestone's own test suite, not a hypothetical.
- **`AddMenu.tsx` was missing most of `CONTRACTS.md` §8's own documented contents — found while comparing against the reference design mock.** The spec already required every type's Add entry to always render, disabled with "Coming soon" for a not-yet-`available` type — the implementation instead showed generic Write/Upload/Import labels swapped per whichever type tab was active, never a specific "Add MCP server"/"Add connector"/"Add plugin" entry, and had no "Create with AI" entry or admin section (Add source / Provision for org) at all. Rewritten to match the mock and plan exactly. `Marketplace.tsx` gained an optional `onCreateWithAi?: () => void` prop, threaded through `AddMenu` — this package still has no LLM-backed draft-generation UI of its own (by design; matching how task F-11 built that flow entirely inside `ai-ui`), so the entry only renders when a host supplies the callback *and* `config.features.create_with_ai` is on. Admin entries (`caller_permissions.can_provision`, `LLD/config-products.md`) are hidden outright for a normal user, not merely disabled — "Add source" itself stays disabled even for an admin (no backing endpoint exists yet, `CONTRACTS.md` §17's own documented-but-unimplemented `/ecosystem/sources`) rather than faking a working action; "Provision for org" navigates to the real `AdminProvisioning` screen rather than being a second, redundant implementation of the same capability.
- **`.storybook/preview.tsx`'s global decorator had the same `initialConfig`-missing bug as the `EcosystemConfigProvider` entry above, in a different place — found while producing UI-vs-mock parity screenshots.** The decorator wrapped every story in `EcosystemConfigProvider` with no `initialConfig`, so any story rendering a leaf screen (anything calling `useConfig()` directly) raced `MockEcosystemClient`'s async `getConfig()` on a cold `iframe.html?id=...` navigation and permanently tripped `EcosystemErrorBoundary` — every affected story silently rendered its "Something went wrong" fallback instead of the real UI (Storybook's own dev UI doesn't surface this as loudly as a script driving it headlessly does). Fixed the same way `renderWithHost()` already had been: pass `initialConfig={MOCK_CONFIG}`.
- **CodeMirror 6 throws under jsdom, not a real bug** — `RectangleMarker`'s cursor/selection measurement pass calls `Range.getClientRects()`/`Element.getClientRects()`, neither implemented by jsdom (a documented jsdom gap). Every `EditContent.tsx` render logged a caught-but-noisy `TypeError` in the test suite's own console output until `test-setup.ts` stubbed both to a no-op empty list — real DOM behavior only matters in the browser-based E2E specs, never in this package's own component tests.
- **`Yours.tsx` crashed the whole screen on one bad row — found live, not by any test, since none exercised a malformed `Install`.** `install.item` is documented (`CONTRACTS.md` §9) and typed (`types.ts`) as always present, but a real backend regression (see `LLD/install-lifecycle.md`) once shipped a row without it, and `InstallRow` dereferenced `install.item.allowed_actions` unconditionally. Fixed two ways, deliberately redundant: `InstallRow` itself now checks for a missing `item` and renders a small "This item is no longer available" placeholder (with a working Remove action) instead of crashing; and a new `EcosystemErrorBoundary` (`components/ErrorBoundary.tsx`) now wraps `Marketplace.tsx`'s own root render, so *any* future rendering bug anywhere in this package's tree degrades to a "Try again" fallback rather than propagating up and blanking whatever the host renders around it. Host-agnostic by design (no host-supplied error-reporting callback required) — `ai-ui`'s own `App.jsx` already wraps its `<Marketplace>` mount in a React error boundary too, at a coarser grain; this one exists so every OTHER host (the F-12 workspace example, any future embedder) gets the same protection without having to remember to add it themselves.

## How to extend

Adding a new screen: read config via `useConfig()`, the client via `useEcosystemClient()`, never take either as a prop. Adding a new item type moving from `coming_soon` to `available`: no code change here at all — `TypeTabs`/`AddMenu`/`CatalogScreen` already read `item_types[].state` live; only a backend config change is needed (`CONTRACTS.md` §8's own design goal). Adding a new theme token: extend `ThemeTokens` in `theme.ts`, update both `LIGHT_TOKENS` and `DARK_TOKENS`, never reference a literal color anywhere else — `check_no_hardcoded_config.py` doesn't check for hex literals directly, but a manual `grep -rn "#[0-9a-fA-F]\{3,6\}" src` sweep (done at the end of this milestone, twice, after two real violations were found and fixed) is worth repeating before considering a future change complete.

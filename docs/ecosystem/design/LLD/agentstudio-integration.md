# LLD — AgentStudio integration (Ecosystem → AgentStudio direction)

**Purpose**: the opposite direction from `LLD/legacy-bridge.md` (which surfaces AgentStudio's own content *into* the Ecosystem catalog, read-only). This file covers the reverse: making Ecosystem-installed capabilities usable *from inside* AgentStudio's own UI and runtime. A 15th LLD file, added in M5 when tasks B-23/B-24 needed a home — none of D-0's original 13 areas fit (matching the precedent `desktop-local-cache.md` set as a 14th, added later for a new area).

## Files / functions

- **Task B-23 — "missing dependency" surfacing**: `AgentStudio/backend/app/engine/native_engine.py`'s `NativeEngine._resolve_catalog_tools()` gains one new optional parameter, `missing_dependencies: Optional[list] = None`. The method's own two existing tool-drop sites (a catalog lookup that raised, or one that returned nothing) each gain one additive line: `if ECOSYSTEM_AGENTSTUDIO_MISSING_DEP and missing_dependencies is not None: missing_dependencies.append(tool_name)`. The flag itself is read defensively — `from core.config import ECOSYSTEM_AGENTSTUDIO_MISSING_DEP` wrapped in `try/except ImportError` (falls back to `False`) — since `AgentStudio/backend/app/core/config.py` is a *separate* config module from the main repo's `core/config.py`, and AgentStudio's standalone dev-mode service (`:8002`, not used by any compose service, per `AgentStudio/backend/Dockerfile`'s own comment) has no path back to the main repo's module at all.
- **Task B-24 — skill picker merges Ecosystem skills**: `AgentStudio/frontend/src/components/common/CatalogPicker.jsx` gains one additive `useEffect`, active only when `kind === "skills"` and the flag is on: calls `platformFetch('/ecosystem/capabilities?surface=agent_studio')` (an existing helper in `AgentStudio/frontend/src/config/api.js`, already used for other main-repo platform endpoints — never a new fetch helper) and merges any results not already present (by `name`) into the SAME `catalog` state array the native `GET /skills-catalog` fetch already populates, each tagged `_ecosystemSourced: true`. That tag drives a small `Marketplace` badge next to the entry's name, both in the attached-chip strip and the add-menu list (`.catalog-picker__ecosystem-badge`, `AgentStudio/frontend/src/index.css`). `GET /skills-catalog` and its response shape are completely untouched — the merge is a second, independent fetch, never a change to the first.
  - **Flag mechanism**: a build-time env var, `VITE_ECOSYSTEM_AGENTSTUDIO_SKILLS`, read via `isEcosystemAgentStudioSkillsEnabled()` — a function, not a module-level `const`, specifically so `vi.stubEnv()` can mock it per-test (a module-level `const` only reads `import.meta.env` once, at first import, which silently defeated an early draft of this task's own tests — see Edge cases). Not a live backend flag lookup: this keeps "flag off → zero extra network calls" trivially true and cheap to verify, rather than requiring the picker to first ask the backend whether to ask the backend.
  - **Not yet built, disclosed**: runtime *execution* of a picked Ecosystem-sourced skill still needs to go through `skill_view`/`read_skill_file` (task B-15) rather than AgentStudio's own `skill_files`/`skills_catalog` tables, per this task's own original instruction ("Runtime loading of an Ecosystem-sourced skill's content, once picked, goes through skill_view/read_skill_file — never a read of skills_catalog/skill_files"). That is a `native_engine.py`-side dispatch change (detecting that an attached skill's name is an Ecosystem namespace, not a native catalog entry, and routing its tool-call execution accordingly) — the same file, and the same risk profile, task B-23 already flagged as too deep/unfamiliar to safely modify further in this pass (it could not even be imported standalone for testing here). This task's own test suite instead proves the one thing it's actually confident is true and safe: **zero writes ever reach `skills_catalog`/`skill_files`** from the picker itself, regardless of which list a picked skill came from — the picker only ever calls `onChange()` with a plain in-memory object, never persists anything on its own (persistence is the parent `ConfigPanel`'s job, mirroring the attached array onto `node.data.{tools|skills}`, per this component's own pre-existing docstring — unrelated to and untouched by this task).

## API and DB changes

None. `_resolve_catalog_tools()`'s own DB reads (`workflow_repo.get_tool()`, AgentStudio's `tools_catalog`) are completely unchanged — this task never writes anywhere, and never touches the Ecosystem catalog's own tables either (that's task B-24's job, via a read-only `GET /ecosystem/capabilities` call, not a DB read from AgentStudio's backend directly).

## Sequence diagrams

```
NativeEngine._resolve_catalog_tools(requested, ..., missing_dependencies=None)
  → for each requested tool name:
      lookup in tools_catalog (async, concurrent via asyncio.gather)
      → found: wrap as _CatalogTool, append to the returned tools list (unchanged)
      → not found / lookup raised:
          log a warning (unchanged, always happens)
          IF ECOSYSTEM_AGENTSTUDIO_MISSING_DEP and a caller passed a list:
            append tool_name to that list  <- the only new behavior
  → return tools  (the SAME list shape as before this task -- never changed)
```

## Edge cases and errors

- **A module-level `const` reading `import.meta.env` silently defeats `vi.stubEnv()`-based test mocking — a real bug caught while writing this task's own test suite, not by review.** An early draft of `CatalogPicker.jsx` read the flag as `const ECOSYSTEM_AGENTSTUDIO_SKILLS = import.meta.env.VITE_ECOSYSTEM_AGENTSTUDIO_SKILLS === 'true';` at module scope — evaluated exactly once, at first import. Vitest's `vi.stubEnv()` patches the live `import.meta.env` object correctly, but that patch happens *after* the module (and its already-evaluated `const`) was first imported, so the component never saw the stubbed value; only the "flag off" test (which happened to match the unstubbed default) passed, while every "flag on" test silently exercised flag-off behavior instead of failing loudly. Fixed by reading the flag inside a function (`isEcosystemAgentStudioSkillsEnabled()`), called fresh on every effect run, at the negligible cost of one extra property read per render.
- **`NativeEngine` is a shared singleton across concurrent requests** (its own docstring cites `self._singleton_tool_cache` — "Singleton tool cache for platform utilities that never change at runtime"). This ruled out the obvious-looking design of recording missing dependencies as instance state (`self.missing_dependencies = [...]`) — that would leak one request's missing-dependency list into a completely unrelated concurrent request's response. The out-parameter design (`missing_dependencies: Optional[list] = None`, populated per-call, never stored on `self`) avoids this entirely — enforced by `test_missing_dependencies_is_never_stored_on_self`, a real regression test for exactly this failure mode, not just a design note.
- **Seven existing call sites, only one signature change, zero behavior change for six of them.** `_resolve_catalog_tools()` has 7 call sites across `native_engine.py`, each in a different execution context (top-level agent run, sub-agent construction, workflow node re-entry, etc.). None of them pass `missing_dependencies` — the parameter's default (`None`) means every one of the drop-site checks (`missing_dependencies is not None`) is false regardless of the flag, so this task changed the *signature* (additive-only, a new optional kwarg) without changing *behavior* at any of the 7 sites.
- **Disclosed, deliberately not implemented in this pass: wiring the signal all the way to a specific user-visible UI surface.** `_resolve_catalog_tools()` now has a real, tested mechanism for a caller to *ask* for the missing-dependency list — but no call site yet actually passes one and threads it into a response the AgentStudio frontend renders. Confidently identifying *which* of the 7 call sites is "the one the calling UI reads from," and what response shape that UI already expects, requires deeper context on `native_engine.py`'s ~8,000-line control flow and its frontend counterpart than this pass could safely acquire without risking a mistake in unfamiliar, live, production code (`native_engine.py` could not even be imported standalone for testing in this environment — see Tests below — underscoring how deep and load-bearing this file's own dependency chain is). This is the resolver-side half of B-23, fully correct and independently useful (any future caller can opt in immediately); the UI-wiring half is a real, named follow-up, not silently dropped.

## Flags

`ECOSYSTEM_AGENTSTUDIO_MISSING_DEP` (`core/config.py`, default off) — task B-23, a backend Python flag, read defensively (see above). `ECOSYSTEM_AGENTSTUDIO_SKILLS` — task B-24, a **frontend build-time** flag (`VITE_ECOSYSTEM_AGENTSTUDIO_SKILLS`, `AgentStudio/frontend`), independent of and not synchronized with any backend flag of the same conceptual purpose — a real, disclosed seam (see How to extend).

## Tests

- `AgentStudio/backend/tests/test_missing_dependency_signal.py` (5 tests, task B-23) — source-string style, matching the existing convention `test_sample_doc.py`'s own native-engine plumbing checks already established in this file (importing `native_engine.py` directly pulls in the main repo's `core.*` stack; confirmed directly — a standalone import attempt from this environment hung rather than completing, even with both the repo root and `AgentStudio/backend` on `PYTHONPATH`). Covers: the flag is read defensively with a fail-closed fallback; the new parameter is optional with a `None` default; both drop sites record when the flag is on and a list was supplied; the original warning logs are untouched; the missing-dependency state is never stored on `self`. `AgentStudio/backend/tests/test_sample_doc.py`'s own 11 pre-existing tests re-run after this change: unaffected.
- `AgentStudio/frontend/src/components/common/__tests__/CatalogPicker.test.jsx` (5 tests, task B-24 — **the first real component test in this frontend package**; `AgentStudio/frontend`'s `vitest.config.js`/`vitest.setup.js` were already configured for this, but no test file had ever been written against that config before this task). Covers: flag off is provably zero ecosystem network calls (not just an empty merge); flag on merges and badges both lists; `kind="tools"` never triggers the merge (skills-only); picking an ecosystem-sourced skill calls `onChange()` with it, with zero `POST` calls; the ecosystem endpoint failing degrades silently, native picker unaffected. `AgentStudio/frontend`'s own build (`npm run build`) re-verified after this change: succeeds.

## How to extend

Wiring B-23's missing-dependency signal to an actual UI surface: identify the specific call site among `_resolve_catalog_tools()`'s 7 that corresponds to "a user is looking at this agent's configuration/run in the UI" (most likely the top-level agent-run entry point, not a sub-agent/workflow-node re-entry path), pass it a list, and thread the result into whatever response schema that endpoint already returns — a scoped follow-up task, not a blind guess. Wiring B-24's runtime-execution half (routing a picked Ecosystem-sourced skill's actual invocation through `skill_view`/`read_skill_file` instead of `skills_catalog`/`skill_files`) needs the same care — identify where `_CatalogTool`'s dispatch decides *how* to fetch a tool/skill's content, and branch on `_ecosystemSourced` (or an equivalent server-side marker persisted alongside the attached skill) before assuming AgentStudio's own tables. Unifying the two independent flags (`ECOSYSTEM_AGENTSTUDIO_SKILLS` frontend build-time vs. a hypothetical backend equivalent) into one source of truth is a real, disclosed gap worth closing before this feature ships broadly — today, a deployment could build the frontend with the flag on while having no backend-side equivalent concept at all (harmless today, since the backend `GET /ecosystem/capabilities` endpoint is unconditionally available regardless of any AgentStudio-specific flag — but worth tightening before this feature is considered fully specified).

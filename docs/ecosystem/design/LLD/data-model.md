# LLD — Data model

**Purpose**: the Postgres schema backing the Ecosystem marketplace — catalog items, versions, installs, sources, and the supporting registries (surfaces, product profiles, publishers). Landed in task B-1 (M1); ORM model coverage extended in M2 as B-9/B-10/B-19 needed to query more tables.

## Files / functions
- `db/migrate.py`'s `_part_ad1_ecosystem_marketplace_tables_2026_09_25()` — the migration itself. Called from `run_migrations()`. Idempotent: every statement is `CREATE ... IF NOT EXISTS` or `INSERT ... ON CONFLICT DO NOTHING`, so re-running it (e.g. on redeploy) is always a clean no-op.
- `db/models.py`'s `Ecosystem*` classes — ORM models for the tables the service layer actually queries so far: `EcosystemPublisher`, `EcosystemSource`, `EcosystemItem`, `EcosystemItemVersion`, `EcosystemGateRun`, `EcosystemGateFinding`, `EcosystemAudit` (M1), plus `EcosystemInstall`, `EcosystemShare`, `EcosystemReport`, `EcosystemFeaturedOverride` (M2, tasks B-9/B-10/B-19). The remaining tables the migration created (`ecosystem_credentials`, `oauth_provider_configs`, `oauth_client_registrations`, `ecosystem_surfaces`, `ecosystem_product_profiles`, `ecosystem_org_products`, `credential_audit`, `desktop_devices`, `ecosystem_drafts`) exist in the schema now but don't get an ORM model until the milestone that first queries them — this file's own convention (see `KnowledgeDocDeletion` for the precedent) pairs a raw-DDL `CREATE TABLE` with an ORM model added only when something needs to query it, rather than declaring every model up front.

## API and DB changes
20 new tables, all additive, none touching `skills_pg`/`skills_catalog`/`cowork_roles`/`connector_definitions`/`CredentialVault`/`user_oauth_tokens`. Full DDL: `docs/ecosystem/ECOSYSTEM_PLAN.md` §4. Two extensions enabled: `pgcrypto` (already present) and `pg_trgm` (new — backs `ecosystem_items`'s trigram search index).

Two seed tables get real rows at migration time, not left empty for a later admin step:
- `ecosystem_surfaces` — 5 rows (`chat`, `agent_studio`, `cowork`, `desktop`, `workspace_chat`).
- `ecosystem_product_profiles` — 2 rows (`enterprise`, `workspace`), matching `docs/ecosystem/CONFIG_AND_PRODUCTS.md` §3's exact feature-flag shapes.
- `ecosystem_org_products` — 1 row (`org_id='default'` → `enterprise`, `is_primary=true`) so an existing single-org deployment has a valid entitlement from day one, never landing on "no primary product" for pre-existing orgs.

`org_id` is `VARCHAR(255)` everywhere, never `UUID REFERENCES ainxt.orgs(id)` — `ainxt.orgs` doesn't exist anywhere in this codebase (verified by full-repo search); every existing multi-tenant-shaped table already uses a plain string `org_id`, and these tables follow that exact convention rather than inventing a new one.

## Edge cases and errors
- **One `local` source per org** (`ux_ecosystem_sources_one_local_per_org`, a partial unique index on `ecosystem_sources(org_id) WHERE kind='local'`) — verified by an actual insert-a-duplicate-and-expect-failure test (`tests/db/test_ecosystem_migration.py::test_one_local_source_per_org_unique_index_enforced`), not just "the index exists."
- **Namespace uniqueness is scope-dependent**, expressed as two separate partial unique indexes rather than one plain `UNIQUE` constraint, because `org_private` items need per-org isolation (two orgs can each have their own `acme/foo`) while every other scope needs global uniqueness (`docs/ecosystem/ECOSYSTEM_PLAN.md` §4's comment above the indexes explains why a single `UNIQUE(namespace, item_type)` can't express this).
- **`ecosystem_installs`/`ecosystem_credentials`'s `UNIQUE NULLS NOT DISTINCT`** requires Postgres 15+ (this repo's CI and this milestone's test environment both use `pgvector/pgvector:pg16`) — without it, Postgres's default `NULLS DISTINCT` would silently allow duplicate org-scoped rows, since `NULL <> NULL` under the default semantics.
- **Critical bug found and fixed in M2, affecting every table in this file**: `db/migrate.py`'s pre-existing `Base.metadata.create_all()` step (early in `run_migrations()`, well before `_part_ad1_...`'s own raw DDL runs) creates a bare version of every table that has a matching ORM model in `db/models.py` — including every `Ecosystem*` model. Because `_part_ad1_...` uses `CREATE TABLE IF NOT EXISTS`, `create_all()` winning the race silently made several constraints described in this file **permanently inert**: `ecosystem_installs`' `UNIQUE NULLS NOT DISTINCT` most notably (the constraint text was correct in the migration file the whole time — it just never actually reached the live table on any database this had run against). Fixed by excluding every `ecosystem_*`/`oauth_provider_configs`/`oauth_client_registrations`/`credential_audit`/`desktop_devices` table from `create_all()`'s table list, mirroring the exact existing precedent for `document_embeddings`/`workspace_messages` in that same code. **Consequence for future work**: any *new* `Ecosystem*` ORM model added to `db/models.py` is now correctly excluded from `create_all()` automatically (the exclusion is prefix/suffix-based, not a hand-maintained list) — but the corresponding raw DDL in `_part_ad1_...` (or whatever migration part supersedes it) is the **only** thing that actually creates these tables' real constraints; `create_all()` must never be relied upon for them, even implicitly.
- **Repair migration for databases that ran the old, buggy `create_all()` before the fix above landed** (`_part_ad2_repair_ecosystem_constraints_2026_09_27()`, immediately after `_part_ad1_...`'s own call in `run_migrations()`): the create_all() fix only changes behavior going forward — it does not retroactively add constraints to a table that a pre-fix run already created. This repair detects, per constraint, whether it's actually present (via `pg_constraint`, not "does the table exist") and adds any of the 15 CHECK / 2 UNIQUE constraints (across 8 tables) that are missing. It never deletes data: if a missing UNIQUE constraint can't be added because real duplicate rows already accumulated while it was inert, it reports the duplicate groups (`GROUP BY ... HAVING COUNT(*) > 1`, which already matches `NULLS NOT DISTINCT` semantics with no special-casing needed) and skips just that constraint, surfacing as a non-zero exit via the existing `_MIGRATION_FAILURES` convention until an operator cleans up the data or sets `MIGRATE_ALLOW_PARTIAL=true`. Safe to run on an already-correct database (every check is a no-op skip) and on every future redeploy. Verified against a real, deliberately-reproduced pre-fix database, not just read for correctness — see `CHANGELOG.md`'s 2026-09-27 entry.

## Flags
None — the schema is always present once migrated; runtime behavior that reads/writes these tables is gated per-task (`ENABLE_ECOSYSTEM_MARKETPLACE`, `ECOSYSTEM_TYPE_*`, etc., all registered in task B-0).

## Tests
`tests/db/test_ecosystem_migration.py` — all 20 tables exist, both seed tables have their expected rows, and the one-local-source-per-org index actually rejects a duplicate insert (not just "exists"). Verified against a real `pgvector/pgvector:pg16` instance: migration runs clean from empty, is idempotent on a second run (no errors, no duplicate seed rows), and all 24 tests in this file pass.

`tests/db/test_ecosystem_migration_repair.py` (4 tests) — covers `_part_ad2_repair_ecosystem_constraints_2026_09_27()` directly: a dropped CHECK constraint gets added back; a second run is a clean no-op; a genuine duplicate blocks only its own UNIQUE constraint (reported, not deleted) and succeeds once the duplicate is removed; an unrelated table's (`users`) constraint set is untouched. Also run against a separately, manually reproduced "old M1" database (a throwaway Postgres 16 instance with `Base.metadata.create_all()` run using the pre-fix table filter) to confirm the repair behaves identically on a genuinely pre-fix database, not just a same-process constraint drop — see `CHANGELOG.md`'s 2026-09-27 entry for the full evidence trail.

## How to extend
Adding a new ecosystem table: add its DDL to `_part_ad1_...` if this is still an active migration window, or start a new dated `_part_<next-letter>1_...` function (check the tail of `db/migrate.py` for the next available label — don't guess) once M1 is closed out and a later milestone needs a schema change. Add the matching ORM model to `db/models.py` only when a service actually needs to query it, per this file's own pairing convention.

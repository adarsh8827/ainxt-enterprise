## 1. Inventory of the merged frontend

**Files changed** (`git diff --name-only main..feature/marketplace-merged`):
- `ai-ui/package.json`, `ai-ui/package-lock.json` — dependency change.
- `ai-ui/src/App.jsx` — route registration.
- `ai-ui/src/components/Chat.jsx` — one new `useEffect` (prefill listener).
- `ai-ui/src/components/Login.jsx` — **unrelated CAPTCHA-disable regression** (see above).
- `ai-ui/src/components/Sidebar.jsx` — one new nav entry.
- `ai-ui/src/components/Marketplace.jsx` — **new file**, 1745 lines, the entire feature.
- `ai-ui/src/marketplaceStore.js` — **new file**, 270 lines, the entire "data layer."

**Dependencies added**: `jszip@^3.10.2` (`ai-ui/package.json` diff) — dual-licensed **MIT OR GPL-3.0**; using it under the MIT option is compliant with the "MIT or Apache-2.0" rule, no action needed beyond a THIRD-PARTY-NOTICES entry (matches the existing precedent already used for other dual-licensed packages per `ECOSYSTEM_PLAN.md` §1.6). No other new dependency. `lucide-react` (already present pre-merge, `ai-ui/package.json` on `main`) gets **one new icon import** in this branch: `Store` in `ai-ui/src/components/Sidebar.jsx` (diff adds `Store,` to the `lucide-react` import block, used for the new "Marketplace" nav item) — this is new *usage* of an existing dependency, and per the phase's "No lucide in new code" rule, this specific icon reference needs to be swapped for the new MIT icon set (§5).

**Routes**: `App.jsx` diff adds `import Marketplace from "./components/Marketplace.jsx"`, a `"/marketplace": "marketplace"` entry in `PATH_TO_VIEW`, and a `<Route path="/marketplace" element={<Marketplace user={user} />} />`. One flat route, no sub-routes (detail/create/upload are all client-side state inside `Marketplace.jsx`, not distinct URLs — see mismatch M1 in §3).

**Nav/sidebar**: `Sidebar.jsx` diff adds one item: `{ view: "marketplace", icon: Store, label: "Marketplace", maxLevel: 6, beta: true }`, placed after "Connectors" and before "Buddy Setup" in the nav array (`ai-ui/src/components/Sidebar.jsx` diff, ~line 105). Gated by `maxLevel: 6` and `beta: true` — same convention as the adjacent "Connectors" item, so it already has a permission-level and beta-flag mechanism, just not the phase's own `ENABLE_ECOSYSTEM_MARKETPLACE`/product-profile mechanism.

**Cross-component coupling**: `Chat.jsx` diff adds a `window.addEventListener("ainxt:chat-draft", ...)` effect (~line 46-50 of the diff) that sets the chat input from a `CustomEvent`'s `detail`. `Marketplace.jsx`'s "Create with AiNxt" button (line 57-60, 382-386) dispatches exactly this event with a **hardcoded prompt string** (`AINXT_SKILL_DRAFT_PROMPT`, line 48-49: *"Let's create a skill together using your skill-creator skill. First ask me what the skill should do."*) and navigates to `/chat`. This is the entirety of the "Create with AI" implementation — it does not call any API, does not stage a draft, does not run a gate, and depends on a chat-side "skill-creator skill" that **nothing in this diff creates or verifies exists**.

**State/data layer**: `ai-ui/src/marketplaceStore.js` is a **complete, self-contained, localStorage-only CRUD layer** with no network calls anywhere (confirmed: no `fetch`/`axios`/`EcosystemClient` reference in either new file). Explicit design note in its own header comment (lines 1-15): *"This Marketplace is a fresh, standalone feature: it does not read from or write to any pre-existing skill/connector/plugin system in this codebase... Until a real backend for THIS feature is built, everything created through the Marketplace UI is persisted to localStorage."* Three item kinds (`skillsStore`, `connectorsStore`, `pluginsStore`), each a generic `makeCrud(key, defaults)` factory (line 106-138) backed by `localStorage` keys `ainxt.marketplace2.{skills,connectors,plugins}` and a separate `ainxt.marketplace2.installed` `Set`. A `parseSkillMarkdown`/`buildSkillMarkdown` pair (lines 63-100) implements a minimal, hand-rolled SKILL.md frontmatter parser (name+description required, everything else ignored) — same class of implementation as `AgentStudio/backend/skill_factory/pipeline.py:179-201`'s regex-based frontmatter parser referenced in `ECOSYSTEM_PLAN.md` §1.1, but independently written, not shared code. Seed data (`refreshSeedData()`, lines 197-270) upserts 6 fictional third-party skills + 3 first-party connectors + 1 plugin on **every module load** (not one-time), with stable ids so re-runs don't duplicate — explicitly documented as intentional for an actively-changing UI-first phase (lines 171-186).

**Where API calls happen**: nowhere. Zero HTTP calls in either new file. This is the single largest fact governing this entire audit — the merged frontend is a **fully offline, single-browser UI prototype**, not a thin client against `CONTRACTS.md`'s API. Every "mismatch" in §3 stems from this.

## 3. Mismatches between the FE and `CONTRACTS.md`

**M1 — No real routing for detail/create/upload states.** The mock uses a single-page-app render function keyed off an in-memory `S` object (`S.detail`, `S.view`, `S.dtab`) with a `copyLink()` that constructs a URL the app doesn't actually route to (`${origin}/customize/${type}/id/${pub}/${id}` — that path isn't wired to `render()` anywhere in the mock either, it's aspirational). The merged FE does the same thing one level up: **one** route (`/marketplace`) with everything else as component state (`detail`, `skillForm`, `skillUploadOpen`). Neither artifact gives you a shareable/bookmarkable/back-button-safe URL for an item detail page, a create form, or an upload flow. **Proposal**: the real implementation should use nested routes (`/marketplace/skills/:namespace`, `/marketplace/skills/new`, `/marketplace/skills/upload`) so Copy Link and browser back/forward work correctly — this is a UI-side change, no `CONTRACTS.md` impact.

**M2 — `CONTRACTS.md`'s `status[]` filter can't express "show me warned/blocked items."** `ItemStatus` = `active|source_unavailable|yanked` (lifecycle of the *catalog entry*), while the mock's badges and the phase's own audit requirement ("filters: category, trust, verification, surface") are about `GateVerdict` = `pass|warn|fail|pending` (the *content* verdict). These are genuinely different axes (matches the trust-tier-vs-verdict separation `ECOSYSTEM_PLAN.md` §2 already calls out as a Hermes-derived principle) and `CONTRACTS.md`'s list-query format currently only exposes one of them. **Proposal**: add `verdict[]` as a sibling query param to `status[]` in `CONTRACTS.md` §5, backed by a join against each item's latest `ecosystem_item_versions.gate_verdict`.

**M3 — Category taxonomy collision.** `marketplaceStore.js:34-37` hardcodes an 11-value, Title-Case taxonomy (`Engineering, Sales, Marketing, ...`) entirely independent of `ECOSYSTEM_PLAN.md` §4.1's 15-value, lowercase-hyphen taxonomy (`productivity, dev-tools, ...`). Neither matches the mock's data either (the mock's seed items use freeform category strings like `'Databases'`, `'Retail & e-commerce'`, `'Tickets & tasks'` — closer to tags than a fixed enum, suggesting the mock's own author treated "category" loosely). **Decision needed in Step 2**: pick one canonical taxonomy and make `GET /ecosystem/config` the single source both UIs render from — none of the three existing lists should survive as-is.

**M4 — "Create with AI" is not the same feature in the FE as in `CONTRACTS.md`/the phase brief.** The FE's version is: click button → dispatch a hardcoded prompt into Chat → navigate to `/chat` → (assumed) some existing chat-side "skill-creator skill" takes over from there with no further Marketplace involvement, no draft object, no gate, no confirm step. The phase brief's version (and the mock's own tooltip text: "opens a chat that drafts the skill, **then a preview card**") is a staged draft → structured preview/edit card → explicit confirm → gate run → private installed item. These are different features that happen to share a button label. **This needs a full rebuild, not an extension** — flagging so Step 3's task breakdown scopes it as new work, not a refactor.

**M5 — License is entirely unmodeled in the FE.** Neither `marketplaceStore.js`'s item shape nor any of the three creation flows (manual form, upload, create-with-AI) collects, validates, defaults, or displays a license. Given the standing rule ("Only MIT or Apache-2.0... required, MIT default"), this is not a cosmetic gap — the current FE provides no mechanism to enforce or even record the one non-negotiable rule of the whole initiative. **Proposal for Step 3**: the license field is mandatory in `SkillFormPage`/`SkillUploadPage`/the create-with-AI confirm card, defaults to MIT, and a non-MIT/Apache-2.0 value in an uploaded `SKILL.md`'s frontmatter (if the phase decides to honor a `license:` frontmatter key at all) must be caught client-side *and* re-validated server-side by the gate — never trust the client value alone.

**M6 — Naming: "Marketplace" (FE) vs "Customize" (mock).** Cosmetic, but worth deciding explicitly rather than by default: the mock's information architecture treats this as a general capability-management surface ("Customize") that happens to have marketplace-shaped browsing inside it, while the FE named the whole feature "Marketplace." `CONTRACTS.md`/`ECOSYSTEM_PLAN.md` don't mandate a UI label. **Recommend**: pick one name for the nav entry and use it consistently in routes, breadcrumbs, and copy — don't ship both.

**M7 — The FE invented a first-party/third-party split (`SkillsHome`) that doesn't exist in the mock or `CONTRACTS.md`.** The mock's Discover layout for every type (including Skills) is: hero → New-{type} section → per-category sections, each with "Show all." The merged FE instead gives Skills a bespoke two-section layout ("Skills created by you" / "Skills from third parties") with an accompanying invented concept — the `ThirdPartyCheckModal` "Legal & compatibility check" (4 static, always-passing checks: License compatibility, Data & privacy review, Security review, Version compatibility) shown once before a third-party skill is first used. This modal is a well-intentioned placeholder for something real (it's clearly gesturing at the same territory as the gate's verification stages) but it's a **parallel, redundant concept** to the gate — the phase brief's actual design already has a verification pipeline with a real, persisted verdict and a Verification tab; a second, separate, client-only "legal check" that always passes would either confuse users (two different "is this safe" mechanisms) or bit-rot into a meaningless click-through. **Recommend REMOVE** `ThirdPartyCheckModal` and the `SkillsHome` first-party/third-party split entirely, replaced by the mock's category-sections layout plus the real Verification tab/blocked-banner/warning-banner mechanism, which already covers everything this modal was gesturing at, with a real backend behind it.

**M8 — Sync vs. async install semantics are undecided.** `CONTRACTS.md` §3 specifies install as async (`{job_id, status:"verifying"}`, final state via `ecosystem.changed` or job polling). Both the FE (`toggleInstalled`, synchronous) and the mock (`quickAdd`, synchronous, immediately flips `installed=true`) model it as instant. For Skills specifically — where gate stages 1-4 (manifest/license/static-safety/supply-chain) can plausibly complete in well under a second, but stage 5 (sandboxed script execution) cannot — **a real "quick add" click will not be instant**, and neither reference artifact shows what the UI does while the job is `verifying`. **Proposal for Step 3**: quick-add optimistically shows a transient "Verifying…" state on the card's action button (not the full-page status card, which is chat-specific) and flips to Added/Blocked when the job resolves, consistent with the phase brief's `POST /ecosystem/items` "always staged, user confirm" language applied to the quick-add path too.

**M9 — No real version history.** FE's `doSaveSkill` mutates the existing localStorage record in place and increments an integer counter (`version: (existing.version||1)+1`) — the *previous* content is gone the instant a new version is "created." `ecosystem_item_versions` (immutable, content-hash-addressed, per `ECOSYSTEM_PLAN.md` §4) is the correct model and requires the FE's edit flow to create a **new** version row rather than update-in-place; this is a backend/data-model requirement more than a UI one, but the UI's Versions tab (ADD, above) can't be built at all until this is fixed.

**M10 — "Delete" vs "Uninstall" are conflated in the FE.** `doDelete` (`Marketplace.jsx:135-147`) permanently removes the item from the shared store for everyone (`tab.store.remove(item.id)`), regardless of whether the caller is deleting their own draft or unlinking their personal install of someone else's published item — because in the FE's single-browser, no-multi-tenancy model these are indistinguishable. In the real system they are very different `allowed_actions` (`uninstall` = remove *my* install record; some other, more restricted action = actually delete/deprecate the underlying item, likely restricted to the owner/admin and probably not exposed as a plain "Delete" at all once other orgs may have installed the same public item). **Recommend**: the real Kebab menu offers "Uninstall" universally (per `allowed_actions`) and a separate, owner-only, more clearly-labeled destructive action (e.g. "Delete this skill" inside the Edit flow, not the everyday kebab) for actually retiring an item — never a single undifferentiated "Delete."

**M11 — Async job / event handling: entirely absent from the FE.** No polling, no WebSocket, no `ecosystem.changed` concept anywhere — `bump()` (a local re-render counter) is the FE's entire "did something change" mechanism, and it only fires from the FE's own actions in the same tab. Nothing here contradicts `CONTRACTS.md`, since the FE simply doesn't attempt this yet — noting it as a full ADD for Step 3, not a mismatch to reconcile.

**M12 — Error codes: not applicable yet.** The FE has no error-code handling at all (its only error surface is `parseSkillMarkdown`'s validation-message array, which is a client-side concept, not a wire error). No reconciliation needed against `CONTRACTS.md` §2's error-code table beyond wiring it up in Step 3.

- **Routes**: the single `/marketplace` path (`App.jsx` diff) is not itself hardcoded-wrong, but per M1 it needs to become a route *tree*, not a single path with internal state machines standing in for pages.

## Summary for review

The merged frontend is a well-built, entirely offline **UI-only prototype** — good interaction patterns in places (the zip-upload flow, the line-numbered instructions editor, the batch-entry validation UX), but it was built with no visibility into `CONTRACTS.md` (its own top-of-file comments say as much explicitly) and diverges from the mock in ways that matter: no trust/license/verification concept at all, a conflated delete/uninstall model, an invented and redundant "legal check" modal, a hardcoded category taxonomy, and a "Create with AI" button that's a chat-prompt hack rather than the staged draft-and-gate flow the rest of the design assumes. None of that is a criticism of the prototype's purpose — it did what a UI-first exploration is supposed to do — but it means Step 3's plan should budget for a substantial rebuild of the creation flows and the entire detail page's tab structure, while keeping the upload flow, the manual-form UX, and the overall page layout largely intact. Separately and independently of this phase: the merged branch also disables the login CAPTCHA, which should be reverted regardless of how the marketplace work proceeds.

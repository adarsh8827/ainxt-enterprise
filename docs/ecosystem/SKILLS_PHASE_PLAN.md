- **Task B-4 — Legacy bridge: explicit idempotent backfill job (adjusted — replaces the earlier "lazy upsert on read" design; further adjusted in the M0 review, see `docs/ecosystem/design/CHANGELOG.md`'s M0-fix entry)**
  - **Why adjusted**: a lazy upsert triggered by a read is a write hiding inside a read path — harder to reason about, harder to test in isolation, and it means the first user to *view* Discover after a legacy skill is created pays an unpredictable write cost. An explicit job is the same idea (a pointer row per legacy item) made visible, schedulable, and re-runnable.
  - Files: `services/ecosystem/legacy_bridge.py` — **reads only** from `skills_pg`/`SkillRecord` (behavioral-type only, per `ECOSYSTEM_PLAN.md` §15 decision 1 — execution-type rows are never surfaced) and AgentStudio's `skills_catalog`/`skill_files` (`AgentStudio/backend/app/core/workflow_repo.py`); a new standalone job/command, `scripts/ecosystem/backfill_legacy_items.py`, does the writing — one idempotent pass that upserts a pointer-only `ecosystem_items` row per legacy skill not yet mirrored (`legacy_source`/`legacy_ref` set, `license='MIT'` — the platform default for content created on the platform, per this task's instruction — and `org`-tier `trust_tier` carrying the legacy skill's own org attribution). **`source_id` (corrected)**: each backfilled item points at *its own org's* `ecosystem_sources` row of `kind='local'` (auto-provisioned per `ECOSYSTEM_PLAN.md` §4's `ux_ecosystem_sources_one_local_per_org` unique index if that org doesn't have one yet — never a single shared "platform" `local` row across orgs, which would misattribute cross-org content and break the per-org uniqueness the schema already enforces). Content itself is still fetched live from the legacy table on every read, never copied into `ecosystem_item_versions`. Re-running the job is a no-op for already-mirrored rows (matched by `legacy_source`+`legacy_ref`). Neither `skills_pg` nor `skills_catalog` is ever written to, by the bridge or the job.
  - **Gate runs in report mode for backfilled items — hiding via `gate_verdict`, not `status` (corrected)**: the job enqueues a normal gate run (B-8/B-9) for every newly-mirrored item. `ecosystem_items.status` stays `'active'` regardless of the verdict — `status` is the catalog entry's own lifecycle (`active`/`source_unavailable`/`yanked`/`deprecated`) and `source_unavailable` specifically means "the upstream source became unreachable," a different axis from a content gate result (per `SKILLS_UI_AUDIT.md` M2's pass/warn/fail/pending-vs-lifecycle distinction, which this task must not blur). Instead, Discover/Yours filtering joins each backfilled item to its latest `ecosystem_item_versions.gate_verdict` and hides any row currently at `'fail'` — the same join B-4's resolver/list-query already needs for the `verdict[]` filter, reused rather than duplicated. A `fail` verdict never writes back to, blocks, or otherwise affects `skills_pg`/`skills_catalog`, which keep working in AgentStudio/Cowork exactly as before regardless of the gate's verdict on the mirror.
  - **Yours representation (renamed in the M0 review)**: legacy items do **not** get a synthesized `ecosystem_installs` row (that would fabricate an install action nobody actually took, corrupting the "installs reflect real actions" invariant everywhere else in this design). Instead, `Yours` gains a 6th, read-only group — **"Available from existing skills"** (renamed from "Available from Agent Studio" — the name must not imply only one legacy source when it covers both `skills_pg` and AgentStudio's `skills_catalog`) — populated directly from `legacy_source`-tagged `ecosystem_items` visible to the caller (via the existing AgentStudio/skills_pg visibility rules, not a new permission model) whose latest gate verdict is not `'fail'`, with no install/uninstall actions available on those rows (only "Open," which deep-links to the item's existing home in AgentStudio/Cowork, not a Marketplace-native detail page).
  - Tests: an idempotency test (running the backfill job twice produces no duplicate rows); a per-org source test (two orgs' backfilled items point at two distinct `local` source rows, never a shared one); a gate-hiding test (a legacy item whose latest `gate_verdict='fail'` is hidden from Discover/Yours while `status` stays `'active'` and its `skills_pg`/`skills_catalog` row and all AgentStudio functionality are provably untouched); a Yours-grouping test for the "Available from existing skills" group, covering both legacy sources.
  - Flag: `ECOSYSTEM_LEGACY_BRIDGE_SKILLS_PG=on`, `ECOSYSTEM_LEGACY_BRIDGE_AGENTSTUDIO=on` (both default on; independently disableable if either backfill needs to be paused without touching the other; disabling does not delete already-backfilled pointer rows).
  - Definition of done: running the backfill job against a populated `skills_pg`/`skills_catalog` produces exactly one pointer row per eligible legacy skill (each pointing at its own org's `local` source row), each gated in report mode, each visible under "Available from existing skills" in Yours unless its latest gate verdict is `'fail'`, with zero writes to either legacy table at any point.

- **Task B-18 — RBAC permissions**
  - Files: `auth/rbac.py` — add `marketplace:add`, `marketplace:share`, `marketplace:provision`, `marketplace:admin_sources`, `marketplace:admin_policy`, `connectors:admin_shared` to the `PERMISSIONS` dict, in the file's existing `"<resource>:<verb>"` string convention (confirmed no collision with any existing key, `ECOSYSTEM_PLAN.md` §1.5). Placement: `marketplace:add`/`marketplace:share` under `developer` (matches the existing `skill:write`/`agent:write` tier — any authenticated developer can create/share their own items by default, further narrowed by org policy per `CONFIG_AND_PRODUCTS.md` §3); `marketplace:provision`, `marketplace:admin_sources`, `marketplace:admin_policy`, `connectors:admin_shared` under `admin` (matches `mcp:approve`/`admin:all`'s existing tier).
  - **M0-review RBAC-tier research (item 7)**: the review asked which role a normal chat user gets by default before deciding whether `marketplace:add`/`marketplace:share` should sit at `viewer` (all authenticated users) or stay at `developer`. Findings, cited: (1) `chat:write` — the permission that actually lets a user send a chat message, as opposed to only viewing one — is itself gated at the `developer` tier, not `viewer` (`auth/rbac.py:36-54` — `viewer` gets only `chat:read`/`*:read` permissions; `developer` adds `chat:write` alongside `agent:write`/`skill:write`/`workflow:write`/`thread:write`). A `viewer`-tier account cannot write a chat message at all — it is a read-only/observer role platform-wide, not what "a normal chat user" means in practice. (2) Every default-provisioning path that creates a real, chat-capable account assigns `role="user"` — self-registration (`routers/auth_router.py:461`, hard-set regardless of what the client requested), LDAP auto-provisioning (`routers/auth_router.py:758`), and first-login generic SSO provisioning (`routers/auth_router.py:1403`, `auth/sso.py:416`) — and `"user"` is a legacy alias for the `developer` tier (`auth/rbac.py:29`, `_ROLE_LEVEL["user"] = 1`). So the default role for a normal (chat-capable) user is already **developer**, not `viewer`. (3) The one exception found: the Azure AD "office" On-Behalf-Of SSO flow specifically provisions new users at `role="viewer"` (`auth/sso.py:770`, via `_upsert_sso_user`) — those accounts start read-only, unable to write a chat message, until promoted; this is a narrow, already-restricted population by design, not "normal chat users." **Decision applied**: keep `marketplace:add`/`marketplace:share` at `developer` (no `auth/rbac.py` change beyond what B-18 already specifies) — this already covers every account capable of using chat in the first place, and widening to `viewer` would be the one write-capable exception carved into an otherwise strictly read-only tier, breaking that tier's existing invariant for no practical gain (the `viewer`-tier population is, by construction, people who can't chat either).
  - Tests: a unit test asserting `get_all_permissions("developer")` includes the two new developer-tier permissions and `get_all_permissions("admin")` includes all six; a regression test confirming no existing role's permission set shrinks.
  - Flag: none.
  - Definition of done: every endpoint in B-6 through B-19 that needs a marketplace permission check has one, sourced from this list, not an ad hoc string.

- **Task B-9 — Gate stages 5-7 (hardened sandbox, ethics, MCP/connector no-op) + content-hash verdict cache**
  - **Sandbox stage, precisely defined for skills (item m)**: a skill has no declared runtime entrypoint the way a plugin/connector/MCP server will — it's instructions plus optional bundled files. The sandbox stage for `item_type=skill` therefore does exactly two things, nothing more: (1) a **syntax/import check** of every bundled script file (parse the file with the appropriate language parser — e.g. `ast.parse()` for Python — and confirm every `import`/`require` target resolves against a fixed allowlist of standard-library and already-approved-dependency modules; a script that fails to parse or imports something unapproved is a `fail`-severity finding, not a warning); (2) if the bundle declares a **test entrypoint** (a manifest field naming a specific file to execute, e.g. `test: scripts/verify.py` — optional, most skills won't have one), that one file is actually executed inside the sandbox, network always off, `read_only=True` rootfs. No other bundled file is ever executed during gating. This is deliberately narrower than a full "run everything" sandbox — a skill's untested scripts are only ever executed later, live, by a real user's tool call, at which point they're still confined to the same skill_view/read_skill_file/code_executor tool boundaries as any other content, not to a gate-time guarantee.
  - Files: new `sandbox/ecosystem_gate_executor.py` extending `sandbox/docker_executor.py`'s `DockerExecutor` with the profile above: `network_disabled` always true (no caller override), `read_only=True` rootfs + writable tmpfs for `/sandbox` (closing the gap noted in `ECOSYSTEM_PLAN.md` §1.5), a timeout/memory profile tuned for install-time scripts rather than short AI-generated snippets; `services/ecosystem/gate/sandbox_stage.py` (syntax/import check + optional test-entrypoint execution, as defined above), `ethics_stage.py` (a fresh-context call via `models/model_router.py` — never the same model/context that authored or reviewed the item), `mcp_connector_stage.py` (always-pass no-op for `item_type=skill`, wired but inert — closes the gap of "silently skipping a stage" vs. "explicitly always-passing one"). `gate_orchestrator.py` gains the `(content_hash, scanner_version)` cache-lookup short-circuit before enqueuing stage 5.
  - **Ethics stage: unavailable reviewer never resolves to `pass` (M0-review correction)**: if the `models/model_router.py` call for the ethics stage fails, times out, or the configured reviewer model is otherwise unreachable, `ethics_stage.py` must record `gate_verdict='pending'` for that stage (not `'pass'` and not a `fail`-by-default either — an inability to review is not itself a finding) and schedule a retry (reusing whatever retry/backoff mechanism the job queue already provides, rather than inventing a new one). The overall gate run's verdict is `pending` for as long as any stage is `pending` — an item never reaches an installable `pass`/`warn` state on the strength of stages that never actually ran. This applies identically to B-22's seeding path (below): a starter skill seeded while the ethics reviewer is unavailable sits at `pending` until a retry succeeds, it is never marked seeded-and-passing by assumption.
  - Tests: a sandbox-escape regression test (a bundled script attempts an outbound network call or a rootfs write outside `/sandbox`; assert both fail); a resource-exhaustion test (oversized/looping script, assert the timeout fires); a cache-hit test (installing an already-gated content_hash a second time does not invoke the sandbox executor at all); an ethics-reviewer-unavailable test (mock `model_router` raising/timing out → assert the stage and overall run verdict are `'pending'`, never `'pass'`, and a retry is scheduled).
  - Flag: none.
  - Definition of done: no bundled script can reach the network or persist a rootfs write regardless of what it attempts; a second install of identical content resolves without a new sandbox run; an ethics-reviewer outage never silently upgrades an item to `pass`.
